# pia-harness

사용자와 함께 확정한 Harness 설계 흐름을 기록한다.

태그 `vX.Y.Z`를 push하면 Actions가 wheel을 만들어 Release에 올린다. `pyproject.toml` 버전과 태그가 같아야 한다.

## 0. 전체 구조

```text
          사용자
            │  Telegram
            ▼
   ┌─────────────────┐
   │       PIA       │  회원 확인 · 메시지 입출력 · 대화 저장소 제공
   └────────┬────────┘
            │ 메시지            ▲ 답변
            ▼                  │
   ┌──────────────────────────────────────────────────────────┐
   │                      pia-harness                         │
   │   사용자별로 한 번에 하나씩 처리 · 처리 중 새 메시지는 합쳐서 다시  │
   │                                                          │
   │   ① 기억        ② 판단          ③ 도구               ④ 답변    │
   │   대화 기록      Jev가 다음      · 읽기: 웹 검색,      LLM이      │
   │   Memory   →   행동 선택   ⇄     본문 추출          → 답변 작성   │
   │   요약          (답변/도구)       (예정: 시세·잔고)     + Turn 저장 │
   │   (12시간 뒤                    · 실행: 주문 (매수·매도,           │
   │    요청 때 Memory 검토)          사용자 확인 후 실행)              │
   │                                · 코딩 (미구현)                   │
   └──────────────────────────────────────────────────────────┘
            │               │                    │
            ▼               ▼                    ▼
      대화 저장소       OpenRouter          Exa(검색) · Jina(본문)
      (PIA 제공)       (Jev · LLM)          pia-broker (종목·현재가·주문)
```

Harness는 **기억하고, 판단하고, 필요하면 도구로 찾아보고, 답하는** 대화 엔진이다. 각 부분의 규칙은 아래 섹션에 있다. ① 기억은 [3](#3-context-구성과-turn-연속성)·[4](#4-compaction과-대화-보존)·[5](#5-장기-memory-관리), ② 판단은 [1](#1-harness-flow-overview), ③ 도구는 [6](#6-도구-사양), ④ 답변은 [1](#1-harness-flow-overview)·[6.1](#61-읽기-도구), 처리 중 새 메시지는 [2](#2-같은-사용자가-처리-중-새-메시지를-보낼-때)번이다.

## 1. Harness Flow Overview

```text
사용자 요청
    ↓
Context 구성 (→ 3, 4)
(대화 기록·Memory·이번 요청·이번에 얻은 도구 결과)
    ↓
◇ Jev가 next_action 하나를 선택
  │
  ├─ 답변 (Turn 종료: 최종 답변 또는 되묻기)
  │    · answer + MemoryAction (NONE / UPDATE / FORGET) (→ 5)
  │        · 일반 질문에 답하기
  │        · 부족한 조건을 사용자에게 질문하기
  │        · 도구로 확인한 결과를 설명하기
  │        → 같은 Jev 응답에서 이번 요청의 MemoryAction도 결정
  │        → LLM이 이번 Turn에서 확보한 자료로 답변 작성
  │        → Harness가 답변의 링크를 출처 번호와 목록으로 정리 (→ 6.1)
  │        → 필요한 Memory 변경 처리
  │        → 사용자에게 전달 → Turn 저장 (→ 3) → 종료
  │
  ├─ 읽기 도구 (→ 6.1)
  │    · 6.1.1 웹 검색 (web_search)
  │        · 뉴스·웹 페이지 후보 찾기
  │        → LLM이 검색어 작성
  │    · 6.1.2 본문 추출 (web_extract)
  │        · 대화에 나온 URL에서 목적에 맞는 부분 발췌 (한 번에 최대 5개)
  │        → LLM이 읽을 URL과 목적 작성
  │    · 그 밖의 도구 ID는 등록할 때 결정
  │        · 시세·잔고·주문 상태 조회
  │        · 공시 등 다른 자료 조회
  │    → Harness가 해당 도구에 직접 요청 ────────────┐
  │                                                │
  ├─ 코딩 도구 (미구현)                            │
  │    · 도구 ID는 등록할 때 결정                    │
  │        · 자료 정렬·계산·분석                     │
  │        · 요청에 맞는 일회성 코드 작성·격리 실행    │
  │    → LLM이 코드 작성                             │
  │    → Harness가 실행 환경에 직접 요청 ───────────┤
  │                                                │
  └─ 실행 도구 (→ 6.2)                            │
       · 6.2.1 주문 (order): 매수·매도               │
       → LLM이 인자 작성                            │
       → 도구가 준비 (확인 대기 또는 되묻기)       │
       → Jev 없이 바로 답변 → Turn 종료            │
                                                   ↓
                                          결과를 Context에 추가
                                                   ↓
                                          Context 다시 구성
                                                   ↓
                                          Jev가 다시 선택

다음 Turn, 확인 대기가 있으면 Jev 선택지에 confirm 추가
  └─ confirm (→ 6.2)
       → Harness가 실행 확정 (→ 2)
       → 저장된 요청 그대로 pia-broker에 요청
       → 결과를 Context에 추가하고 Jev 없이 바로 답변 → Turn 종료
```

**구현 현황**: 구현된 분기는 답변, 읽기 도구, 실행 도구(주문)다. 코딩 도구는 목표 설계다. 실행 도구는 선택돼도 바로 실행하지 않고 확인 대기만 만든다. 사용자가 다음 Turn에서 동의해 Jev가 `confirm`을 고를 때만 실행한다. 읽기 도구는 실행 확정 전에 실행되므로, 주문·취소처럼 상태를 바꾸는 작업을 읽기 도구로 등록하지 않는다.

**답변만 종료 지점**이다. 읽기·코딩·실행 도구의 결과는 모두 이번 Context에 추가하고 Jev가 다음 행동을 다시 선택한다. 네 분류는 이해를 돕는 묶음이며, `next_action`의 실제 값은 `answer`, 현재 등록된 도구 ID, 대화에 이번 Turn에 아직 안 읽은 링크가 있을 때의 `web_extract`, 또는 확인 대기가 있을 때의 `confirm`이다. 선택지의 표시 조건은 대화에 보이는 것이나 명시한 안전 규칙에만 묶고, 그 Turn 안에서만 있는 숨은 상태에 묶지 않는다. `MemoryAction`은 `answer`를 선택한 같은 Jev 응답에서만 적용하며, 도구를 선택한 동안에는 `NONE`으로 미룬다. Jev는 이번 요청의 사용자 메시지(처리 중 합쳐진 메시지 포함)와 이번 Turn의 도구 요청·결과를 보고 판단한다. 이번 요청 앞에는 받은 시각(`[Received 2026-09-28 14:05 KST. This is the current time, not the as-of date of any source.]`)을 붙인다. 모델은 오늘 날짜를 모르기 때문이며, 자료의 기준일로 오인하지 않도록 현재 시각임을 밝힌다. 저장되는 Turn에는 붙이지 않는다. 이번 Turn의 도구 결과는 자르지 않고 전부 준다(깊은 조사의 근거가 모두 여기에 쌓인다). 직전 완료 Turn 1개(사용자 메시지·최종 답변)는 "10주", "응" 같은 짧은 후속 메시지를 해석하기 위한 참고로만 함께 주며, 합계 4,000자를 넘으면 요청의 앞부분과 답변의 끝부분만 남긴다. `MemoryAction`은 이번 요청만 근거로 한다. 더 오래된 대화 기록·Memory·요약은 답변 LLM에만 전달한다. 되묻기도 `answer`로 하고 Turn을 끝내며, 사용자의 대답은 다음 Turn에서 직전 Turn과 함께 해석된다.

Harness는 도구에 직접 요청하고 결과를 받아 다음 판단에 연결한다. PIA는 도구 요청을 매번 중계하지 않고 사용자 요청의 채널 입구와 최종 답변 전달을 맡는다. 주문 조건의 최종 검증과 처리는 pia-broker가 맡는다. **실행권 확정은 Harness 내부에서 이번 작업을 더 이상 새 메시지로 취소하지 않기로 하는 단계**이며, 사용자에게 추가 승인을 요청한다는 뜻이 아니다. 조사는 세 한도 중 먼저 닿는 곳에서 멈춘다: 읽기 도구 20회, 읽기 라우팅 시간 60초, Jev 요청 크기(질문·선택지 포함 UTF-8 64,000바이트). 읽기 도구의 필수 인자가 비어 있거나, 본문 추출이 새로 읽을 링크 없이 이미 읽은 링크만 요청한 경우(더 읽을 것이 없다는 뜻)도 같다. 어느 경우든 실패로 끝내지 않고, 그때까지 완료된 결과와 "조사가 한도로 끝났으니 확인하지 못한 부분을 밝히라, Memory는 바꾸지 않았다"는 알림으로 답변을 만든다(`MemoryAction`은 `NONE`). 개별 Jev·공급자 장애와 주문 `confirm`은 이 경로로 바꾸지 않는다. 도구를 자동 재실행하지 않는다.

## 2. 같은 사용자가 처리 중 새 메시지를 보낼 때

```text
같은 사용자의 이전 메시지 처리 중
                ↓
          새 메시지 도착
                ↓
        ◇ 현재 처리 단계? — 코드의 if문
          ├─ 답변 생성 중
          │    → 이전 생성 취소
          │    → 미완료 입력과 새 입력을 합쳐 다시 생성
          │
          └─ 실행 확정 후 (주문의 confirm 선택 시점부터, 또는 답변 전달·저장 단계)
               → 진행 중인 작업은 마침
               → 새 메시지는 다음 작업으로 대기
```

처리 중인 작업이 없으면 바로 새 답변 생성을 시작한다. 한 사용자에게 진행 중인 답변 생성은 한 번에 하나이며, 다른 사용자들의 작업과는 별도로 관리한다. 단계 확인은 LLM이 아닌 Harness 코드가 한다.

## 3. Context 구성과 Turn 연속성

```text
새 사용자 요청
      ↓
Context 구성
  System 지침
  Memory
  Summary
  이전 완료 Turns  (사용자 요청 + 최종 답변)
  이번 사용자 요청 + 이번 Turn의 도구 결과(있다면)
      ↓
◇ 모델 호출 직전 입력 크기 확인 — 코드의 if문
  ├─ 충분함 → 모델 호출
  └─ 너무 큼 → 4. Compaction 진행
               → Context 다시 구성 → 크기 재확인
      ↓
모델 판단
  ├─ 읽기 도구 요청 → 결과를 이번 Context에 추가
  │                  → Context 구성으로 돌아감
  └─ 최종 답변 → 이번 Turn 저장 (사용자 요청 + 최종 답변)
                  → 다음 요청의 '이전 완료 Turns'에서 읽음
```

System 지침은 host가 제공하는 규칙이다. Memory는 오래 기억할 사용자 정보, Summary는 오래된 대화의 요약이며, 둘 다 없으면 Context에서 생략한다. 이전 Turns·이번 요청·도구 결과도 모델이 참고할 데이터이지 System 지침이 아니다.

**입력 예산은 모델의 전체 Context 한도에서 답변용 예약을 뺀 값**이다. 크기 판정은 코드가 하고, Summary 생성에 LLM을 사용한다. 최종 답변 뒤 별도 Compaction 검사는 하지 않고 다음 모델 호출 직전에 확인한다.

## 4. Compaction과 대화 보존

Turn은 한 번의 사용자 요청과 최종 답변을 묶은 기록이다. 그 과정의 도구 요청·결과는 이번 Turn의 판단과 답변에만 쓰고 저장하지 않는다. Memory는 오래 기억할 사용자 정보이고, Summary는 오래된 대화의 압축본이다. 서로 다른 데이터다.

```text
모델 호출 직전, Context 크기를 코드로 확인
  ├─ 입력 예산의 약 80% 미만 → 그대로 모델 호출
  └─ 약 80% 이상
       ↓
    오래된 대화를 줄이기 전에,
    아직 Memory에 반영되지 않은 이전 대화에서
    오래 기억할 내용이 있는지 5. Memory 관리 흐름으로 확인·갱신
       ↓
    완료된 Turns를 두 그룹으로 나눔
      · 남김: 가장 최신 Turn은 반드시 유지하고,
              그 앞의 최근 Turns는 Context 한도의 12.5%에
              들어가는 만큼 유지 (고정된 개수가 아님)
      · 요약: 나머지 오래된 Turns
       ↓
    기존 Summary + 요약할 Turns → LLM이 새 Summary 생성
       ↓
    새 Summary가 비어 있지 않고 원본보다 짧은지 확인
       ↓
    새 Summary를 DB에 저장
      · 성공: 기존 Summary 하나를 교체한 뒤,
              새 Summary에 포함된 원본 Turns를 DB에서 삭제
      · 실패: 기존 Summary와 원본 Turns를 그대로 유지
       ↓
    새 Summary + 남긴 Turns + 이번 요청·도구 결과로
    Context를 다시 구성하고 크기를 재확인
      · 들어감: 모델 호출
      · 여전히 초과: 이번 요청 중단
```

Summary는 세션마다 현재본 **하나**를 저장한다. 다음 Compaction은 이전 Summary와 새로 오래어진 Turns를 합쳐 새 Summary로 **교체**하며, 과거 Summary 버전을 쌓지 않는다. 요약에 포함된 원본 Turns는 새 Summary 저장 성공 후 삭제되므로, Summary에 담기지 않은 오래된 세부사항은 복원할 수 없다.

최근 Turns는 12.5%라는 크기 몫으로 선택하므로 남는 **개수는 일정하지 않다**. 요약되지 않은 Turn은 PIA가 정한 보존기간(기본 30일)의 적용을 받고, 요약된 Turn은 그보다 일찍 삭제된다. 따라서 DB에는 장기 Memory, 세션의 현재 Summary, 남겨 둔 원본 Turns가 주로 남으며 **전체 대화 원문 이력을 보관하는 구조가 아니다**. 장기 Memory는 Compaction이 직접 삭제하지 않는다. 이번 요청과 아직 끝나지 않은 도구 사용은 오래된 완료 Turns를 고르는 대상이 아니다.

## 5. 장기 Memory 관리

Turn은 한 번의 대화 기록이고 Summary는 오래된 대화의 요약이다. **Memory는 이후 대화에 오래 도움이 될 사용자 정보를 담는 별도 문서**로, 사용자마다 현재본 하나만 두며 최대 4,000자다. 내용을 바꿀 때는 문서 전체를 교체하고 과거 버전을 쌓지 않는다.

```text
Memory 검토가 시작되는 세 경우
  ├─ 사용자가 “기억해줘 / 일부 잊어줘”라고 요청
  │    → 최종 answer를 고르는 Jev가 UPDATE / FORGET 선택
  │    → 방금 받은 메시지도 Memory 작성에 포함
  ├─ 반영 여부를 확인하지 않은 완료 대화가 남아 있고,
  │   그중 가장 최근 대화로부터 12시간 이상 지난 뒤
  │   사용자가 다시 메시지를 보냄
  │    → 별도 타이머 없이 그 요청을 처리할 때 검토
  └─ Compaction 직전
       → 반영 여부를 확인하지 않은 완료 대화가 있으면 검토
                    ↓
          변경이 필요할 때 같은 Memory 작성으로 이어짐
                    ↓
       PIA의 금융 투자용 Memory 지침
       + 현재 Memory 문서 + 검토할 대화
                    ↓
       ◇ 명시적 MemoryAction인가? — 코드의 if문
         ├─ UPDATE / FORGET → LLM이 새 Memory 문서 전체 작성
         └─ 자동 검토 → ◇ Jev AI가 변경 필요 여부 판단
                       ├─ 불필요 → Memory 문구 유지
                       └─ 필요 → LLM이 새 Memory 문서 전체 작성
       → 새 문서를 작성한 경우에만 최대 4,000자인지 검증 후 교체
                    ↓
       마지막으로 검토한 대화 위치를 함께 저장
       → 같은 대화를 반복 검토하지 않음
```

PIA는 “금융 투자 에이전트가 장기적으로 기억할 내용”을 정한 Memory 지침을 Harness에 반드시 전달한다. 범용 Harness에는 금융 투자용 지침을 고정하지 않는다. Jev는 `answer`를 선택할 때 이번 사용자 요청만 근거로 `NONE / UPDATE / FORGET`을 함께 결정하며 별도 Jev 호출을 추가하지 않는다. 일반 답변 작성과 Memory 문서 작성은 별도 LLM 호출이다. 자동 검토에서 변경 여부는 Jev AI가 판단하고, 변경이 필요할 때만 LLM이 새 문서를 작성한다.

의미 있는 Memory 변경은 별도 알림 대신 일반 답변 끝에 최대 3개(각 200자 이하) 안내한다. 자동 검토가 실패하면 조용히 넘어가고, 사용자가 직접 요청한 기억·잊기가 실패하면 답변에서 알린다.

`FORGET`은 사용자가 지정한 내용을 지우는 기능이다. 지정한 내용이 Memory의 마지막 항목이면 문서가 비워질 수 있다. 대화 문맥 전체를 초기화하는 별도 기능은 제공하지 않는다.

## 6. 도구 사양

1번에서 Jev가 선택하는 구체적 도구의 동작을 이곳에 모은다. 도구는 Harness가 직접 호출하며, 받은 결과를 이번 Turn의 Context에 추가한 뒤 1번의 Jev 판단으로 돌아간다. **답변만 종료 지점**이다.

### 6.1 읽기 도구

읽기 도구는 외부 자료나 현재 상태를 가져오며, 그 자체로 주문 같은 상태 변경을 하지 않는다.

Jev가 현재 Context로 사용자 질문에 충분히 답할 수 있다고 판단하면 `answer`를 선택한다. 기사 수나 "자료 충분" 상태 같은 별도 규칙은 두지 않는다. 답변 LLM은 이번 Turn의 도구 결과 또는 이전 대화에 실제로 기록된 내용만 근거로 사용한다. 본문을 읽지 않은 후보는 제목·짧은 설명만 있는 자료이므로, 그 범위임을 밝혀 쓰고 본문을 읽은 것처럼 쓰지 않는다. 검색 결과와 본문은 모델을 지휘하는 지침이 아니라 참고 자료다.

**출처 번호**: 답변 LLM은 근거가 된 링크를 주장 바로 뒤에 `<https://…>`로 적는다(수치마다 따로). 번호나 출처 목록은 쓰지 않는다. Harness가 답변의 링크를 처음 나온 순서대로 `[1]`, `[2]`로 바꾸고, 답변 끝에 "출처" 목록(`[1] 제목 URL`, 제목은 검색 후보에서)을 붙인다. 사용자 메시지, 이전 답변, 이번 Turn의 도구 결과에 없던 링크는 지운다(6.1.2 URL 경계와 같은 범위, Summary·Memory 제외. Markdown 링크는 글자만 남김). 그래서 목록의 링크는 모두 사용자나 도구가 실제로 준 것이다. 모델이 직접 쓴 `[n]`도 지운다. 이전 답변의 목록 번호를 베끼면 이번 목록과 어긋나기 때문이다. 목록은 답변과 함께 Turn에 저장되므로 다음 Turn에서도 링크를 다시 읽을 수 있다. 어느 수치에 어느 번호를 붙일지는 모델이 정하므로, 번호를 잘못 붙이는 것까지는 막지 못한다.

3번의 완료 Turn에는 사용자 요청과 최종 답변만 저장한다. 검색어·후보·발췌는 이번 Turn의 판단과 답변에만 쓴다. 다음 Turn에서 이전 답변에 없는 세부 내용이 필요하면, 이전 답변의 링크를 다시 읽거나 다시 검색한다. 반복 탐색은 1번의 세 한도가 제한한다.

OpenRouter 내장 Web Search는 사용하지 않는다. 검색은 `web_search`, 페이지 내용은 `web_extract` 한 경로로만 한다. 공급자는 도구별로 하나씩 고정하고 대체 공급자는 두지 않는다.

#### 6.1.1 웹 검색

웹 검색(`web_search`)은 뉴스를 포함한 웹 전체에서 후보를 찾는 읽기 도구다. 공급자는 Exa의 공개 MCP 서버(`web_search_exa`)이고 키 없이 부른다. 키를 쓸 때도 같은 주소에 `x-api-key` 헤더만 붙인다. 검색 한 번에 후보를 최대 5건 받으며, 후보에는 본문이 없다. 본문이 필요하면 Jev가 6.1.2 본문 추출을 따로 선택한다.

```text
◇ Jev가 web_search 선택
    ↓
LLM이 검색어를 작성
  · 앞선 결과에서 아직 확인되지 않은 부분을 찾음
  · site:example.com, "정확한 구문" 같은 연산자 사용 가능
    ↓
Harness가 Exa MCP를 1회 호출 (numResults=5)
    ↓
후보 최대 5건
  · 제목·링크·날짜(있으면)·짧은 발췌 (본문 없음)
  · 이번 Turn에서 이미 받은 링크는 제외
    ↓
검색어와 후보를 이번 Turn의 Context에 추가
    ↓
◇ Jev가 다시 선택
  ├─ 더 찾을 필요가 있음 → web_search (다른 검색어)
  ├─ 페이지 안의 내용이 필요함 → web_extract
  └─ 답변하기에 충분함 → answer + MemoryAction
```

MCP 응답은 결과를 합친 텍스트다. `---`로 나뉜 블록마다 `Title:`, `URL:`, `Published:`, `Highlights:` 뒤를 읽고, URL이 없는 블록은 버린다. 텍스트가 있는데 후보를 하나도 읽지 못하면 "검색 결과를 해석하지 못함"을 글자 수와 함께 결과로 돌려준다. 응답에는 검색어·본문이 들어 있을 수 있어 내용은 적지 않는다. HTTP 오류·한도 초과·오류 응답도 결과 문장으로 돌려주며, 코드 오류만 Turn을 끝낸다. 후보의 날짜가 Context에 함께 들어가므로 최신성은 Jev와 답변 LLM이 날짜를 보고 판단한다.

#### 6.1.2 본문 추출

본문 추출(`web_extract`)은 **대화에 나온 URL**의 페이지를 읽고, 목적(goal)에 맞는 **요약과 원문 근거**를 가져오는 읽기 도구다. 이번 메시지, 이전 요청·답변, 이번 Turn의 도구 결과(검색 후보, 본문 추출의 확인된 근거)에 있는 링크(Markdown 링크 포함)를 읽을 수 있다. 근거에 적힌 링크는 페이지에 실제로 있던 것이라, 기사에 걸린 공식 페이지를 따라가는 데 쓸 수 있다. 한 링크는 한 Turn에 한 번만 읽는다(몇 초 안에 같은 페이지를 다시 읽어도 결과는 같다). Summary와 Memory는 모델이 쓴 글이라 대상에서 뺀다.

```text
◇ 대화에 이번 Turn에 아직 안 읽은 링크가 있나?
  └─ 없으면 web_extract 선택지를 보여 주지 않음
    ↓ 있음
◇ Jev가 web_extract 선택
    ↓
LLM이 인자 작성 { urls: [1~5개], goal: 찾을 내용 }
  · 대화에 나온 링크를 그대로 복사
    ↓
Harness가 URL마다 (동시에)
  ├─ 대화에 없는 URL → 읽지 않음 (결과에 URL을 다시 적지 않음)
  ├─ 이번 Turn에 이미 읽은 URL → 다시 읽지 않음
  └─ 그 밖 → Jina Reader로 페이지 받기 → 링크 URL·이미지 제거 → 앞 30,000자 → 요약 LLM(goal·사용자 요청·페이지만 봄) → 근거 원문 대조
    ↓
URL별 상태 줄 + 페이지별 요약·검증된 근거(합계 약 2,000자)를 이번 Turn의 Context에 추가 (원문은 넣지 않음)
    ↓
◇ Jev가 다시 선택
```

- **앞에 인자 LLM, 뒤에 정리**: 페이지 원문은 Context에 넣지 않는다. 넣으면 이후 모든 단계(Jev, 인자 LLM, 답변 LLM)가 수만 자를 매번 다시 읽는다. 뒤 단계 LLM은 goal, 이번 사용자 요청, 페이지만 받고 요약(goal 기준 정리, 페이지에 없는 것 포함)과 근거(원문 그대로 복사한 구절)를 돌려준다. 요약의 링크는 지운다. 수치·날짜는 근거에서만 인용하도록 결과 머리말에 적는다. 출력이 잘리면 한 번 더 시도한다.
- **원문 대조**: 근거 구절마다 페이지(링크 URL을 뺀 앞 30,000자)에 실제로 있는지 코드가 확인한다. 공백 차이만 무시한다. 없는 구절만 빼고 나머지는 쓴다. 바뀐 수치나 지어낸 링크가 답변과 읽기 허용 목록에 들어가지 않게 하기 위해서다. 확인된 근거가 하나도 없으면 요약도 싣지 않는다. 요약은 모델이 쓴 글이라 근거 없이는 증거가 아니기 때문이다. Markdown 링크의 URL은 이미 지웠으므로, 결과에 남는 링크는 페이지 본문에 그대로 적힌 URL이 확인된 근거에 들어 있을 때뿐이다.
- **URL 경계**: 대화에 실제로 나온 링크만 읽는다. 악의적인 페이지가 사용자 정보를 담은 새 URL을 만들게 유도해도, 그 URL은 대화에 없으므로 읽지 않는다. 거부한 URL은 결과에 다시 적지 않는다. 결과에 적힌 링크는 다음 호출에서 읽을 수 있게 되기 때문이다.
- **상태 줄**: 읽음(근거 N개, 페이지에 없어 뺀 수, 앞 30,000자만 읽음) / 읽었지만 확인된 근거 없음(인용할 것 없음) / 목적에 맞는 내용 없음 / 앞 30,000자에서 찾지 못함(나머지는 확인 못 함) / 읽지 못함 / 이미 읽음(개수만). 잘린 페이지는 "없음"이라고 단정하지 않는다.
- **실패**: 페이지를 받지 못함(연결·상태 코드·빈 응답), 링크·이미지를 빼니 글자가 없음, 요약 LLM 실패는 `PageReadError`로 "읽지 못함" 결과가 된다. 그 밖의 오류는 코드 오류로 보고 Turn을 끝낸다. 깨진 도구를 Jev가 모른 채 계속 고르지 않게 하기 위해서다(6.1.1과 같은 규칙).
- **공급자**: Jina Reader(`POST https://r.jina.ai/`)를 키 없이 부른다. 우리 서버는 Jina에만 접속하고 redirect는 따르지 않는다. `DNT: 1`로 캐시·기록을 막는다. 키를 쓸 때는 `Authorization` 헤더를 붙인다.
- Jev는 "예전 대화를 가리키면 answer" 규칙의 예외로, 링크의 본문을 읽어 달라는 요청이고 `web_extract`가 있으면 `web_extract`를 고른다.

### 6.2 실행 도구

실행 도구는 주문처럼 상태를 바꾸는 도구다. **항상 사용자 확인을 받는다.** 도구가 선택되면 실행하지 않고 확인 대기를 만들며, 다음 Turn에서 사용자가 동의할 때만 실행한다.

```text
[Turn 1] ◇ Jev가 실행 도구 선택
    ↓
LLM이 인자 작성 → 도구가 준비
  ├─ 부족·모호 → 도구 결과 "무엇이 필요한지" → 바로 답변(되묻기) → 종료
  └─ 준비됨 → 확인 대기 저장 + 도구 결과 "확인 대기: 요약"
    ↓
Jev 없이 바로 답변 → 답변 맨 끝에 도구가 만든 확인 문장 → 종료

[Turn 2] ◇ 확인 대기가 있고 5분 이내인가?
  ├─ 5분 지남 → 버리고 답변 끝에 "확인 시간이 지났습니다. 다시 요청해 주세요."
  └─ 이내 → Jev 선택지에 confirm 추가
            ├─ confirm   → 실행 확정 → 저장된 요청 그대로 실행 → 결과로 바로 답변
            ├─ 같은 도구 → 조건 변경("28만원에") → 새 확인 대기로 교체
            └─ 그 밖     → 일반 처리
    ↓
Turn이 끝나면 확인 대기는 쓰였든 아니든 버림 (새로 만든 것만 남음)
```

- 준비 뒤에는 Jev를 다시 부르지 않는다. 준비 결과는 늘 확인 문장이나 되묻기라 다음 행동이 답변뿐이다. 실제 시나리오에서 Jev가 요청이 남아 있다는 이유로 같은 도구를 계속 골라 시간 제한까지 반복했기 때문이다.
- 실행 도구를 고른 Turn과 `confirm` Turn의 MemoryAction은 `NONE`이다. 같은 메시지의 명시적 Memory 요청("주문하고 이것도 기억해줘")은 바로 반영하지 않고, 저장된 Turn을 보는 자동 Memory 검토(→ 5)에서 반영된다.
- 확인 대기는 사용자당 하나이며 Harness 메모리에만 둔다. Bot이 재시작되면 사라지고, 사용자가 다시 요청하면 된다.
- `confirm`은 모든 실행 도구가 함께 쓰는 선택지 하나다. 설명은 "확인 대기 요약 + 현재 메시지가 정확히 이 작업에 분명히 동의할 때만 선택, 조건을 바꾸면 도구를 다시 선택"이다.
- `confirm`을 고르면 Harness가 실행을 확정한다(→ 2). 이때부터 새 메시지는 기다리고, 읽기 라우팅 시간 제한은 적용하지 않는다. 저장된 요청을 다시 작성하지 않고 그대로 실행하며, 결과를 Context에 넣고 Jev를 다시 거치지 않고 답변한다.
- 확인 문장은 LLM이 아니라 도구가 인자로 만든다. Harness가 답변 맨 끝에 따로 붙여 Turn에 저장한다. Memory 안내 목록과 달리 개수 제한으로 밀려나지 않으므로, 다음 Turn에서 Jev가 보는 직전 답변(3번, 끝부분 유지)에 남는다.
- 되묻기도 `answer`로 Turn을 끝낸다. 사용자의 대답("10주", "응")은 다음 Turn에서 직전 Turn과 함께 해석한다. 다음 Turn에 필요한 내용(모호한 종목 후보 등)은 답변 본문에 들어가야 한다. 도구 결과는 Turn에 저장되지 않는다.
- 실행 뒤 답변 생성이 실패하면 LLM 없이 도구의 고정 결과 문장을 보낸다. 실행 함수는 요청을 보낸 뒤에는 예외를 내지 않고 결과 문장을 돌려준다.

#### 6.2.1 주문

pia-broker의 내부 경로로 한국 주식을 매수·매도한다. Harness는 AWS를 모르며, PIA가 Broker 주소와 요청 서명(httpx auth)을 넘겨준다. 회원 ID는 `user_key`다.

```text
◇ Jev가 order 선택
    ↓
LLM이 인자 작성 { name, side, quantity, order_type(기본 LIMIT), price }
  · name은 공식 종목명(삼전 → 삼성전자, 하닉 → SK하이닉스). 사용자가 코드를 말했을 때만 코드
  · 대화 전체에서 채움 ("3주" 같은 짧은 대답은 직전 주문 요청을 이어감)
  · 매수/매도·수량·가격은 지어내지 않고, 말하지 않았으면 null
    ↓
◇ name · side · quantity가 있나? 없으면 "부족한 인자" → 되묻기
    ↓
Broker 종목 찾기
  ├─ AMBIGUOUS → 후보 목록 → 되묻기 (답변에 후보 이름을 적음)
  ├─ NOT_FOUND → 공식 종목명을 되묻기
  └─ FOUND
    ↓
Broker 현재가 (계좌 미연결이면 "Member Web에서 연결·확인 필요" → 답변)
  · 지정가인데 가격이 없으면 현재가
    ↓
확인 대기 { 주문 내용, request_id(새로 만듦) }
확인 문장:
  "삼성전자(005930) 10주를 285,500원 지정가로 매수할까요? (09:31 기준 현재가 285,500원)"
  "삼성전자(005930) 10주를 시장가로 매수할까요? (예상 금액 약 2,855,000원, 09:31 기준 현재가 285,500원)"
```

- 지정가가 기본이고, 시장가는 사용자가 요청할 때만 쓴다.
- 실행 결과 문장:
  - ACCEPTED: "주문이 접수되었습니다: 요약 (주문번호 …). 체결 여부는 증권사 앱에서 확인해 주세요."
  - REJECTED: "주문이 거부되었습니다: 요약. 사유: KIS 거부 문구(없으면 code)"
  - 그 밖(UNKNOWN, 응답 오류, 통신 실패): "주문 결과를 확인하지 못했습니다: 요약. 주문이 들어갔을 수 있으니 다시 주문하기 전에 증권사 앱에서 꼭 확인해 주세요." 자동으로 다시 보내지 않는다.
- 같은 확인 대기를 두 번 실행해도 같은 `request_id`라 Broker가 한 번만 주문한다.
- 범위는 매수·매도다. 취소·체결 조회·잔고는 나중에 한다.

## 기타: 지원 계약

아래 항목은 위 대화 흐름을 새로 나누지 않는 기본 계약이다.

- Harness는 모델 응답을 검증하고 실패 단계를 구분해 PIA에 알린다. 모델 요청의 재시도는 제한적이며, 실패한 도구를 Harness가 자동으로 다시 실행하지 않는다.
- Jev가 다음 행동을 고르지 못하면 `answer + NONE`으로 우회하지 않고 실패 상태를 PIA에 전달한다.
- Harness는 등록된 도구의 입력을 확인하고 도구 API를 직접 호출한다. pia-broker는 계좌 연결·중복 주문 방지 등 주문 처리 규칙을 최종 확인한다(금액 한도는 두지 않는다). 알려진 실패나 결과 미확정도 Harness가 도구 결과로 다뤄 Jev의 다음 판단에 제공한다.
- 저장소는 사용자별 데이터 분리, Turn 순서·만료, 조건부 갱신을 지킨다. 회원 상태에 따른 대화 중단과 계정 데이터 삭제는 PIA가 맡는다.
- 진행 중이라는 안내와 오류 문구를 사용자 채널에 어떻게 보여줄지는 PIA가 정한다. Harness는 필요한 결과 상태와 선택적 진행 신호만 전달한다.
- 진행 신호: Jev가 고를 때마다 `ConversationStep(next_action, arguments_json)`을 보낸다(인자가 있는 도구는 인자를 만든 뒤, 실행 전). 고른 것일 뿐 실행 결과가 아니다(`confirm`을 골라도 새 메시지로 취소될 수 있다). 단계를 하나라도 보냈으면 Turn 끝에 `None`을 보낸다. 신호는 최선 노력이라 실패하거나 5초를 넘겨도 Turn은 계속된다. Harness는 로그를 남기지 않는다.
