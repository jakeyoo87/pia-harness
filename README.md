# pia-harness

사용자와 함께 확정한 Harness 설계 흐름을 기록한다.

태그 `vX.Y.Z`를 push하면 Actions가 wheel을 만들어 Release에 올린다. `pyproject.toml` 버전과 태그가 같아야 한다.

## 0. 전체 구조

```text
          사용자
            │  Telegram
            ▼
   ┌─────────────────┐
   │       PIA       │  회원 확인 · 메시지 입출력 · 대화 저장소 제공
   └────────┬────────┘
            │ 메시지            ▲ 답변
            ▼                  │
   ┌──────────────────────────────────────────────────────────┐
   │                      pia-harness                         │
   │   사용자별로 한 번에 하나씩 처리 · 처리 중 새 메시지는 합쳐서 다시  │
   │                                                          │
   │   ① 기억        ② 판단          ③ 도구               ④ 답변    │
   │   대화 기록      LLM이 다음      · 읽기: 뉴스·웹 검색, 같은 LLM이 │
   │   Memory   →   행동 선택   ⇄     본문 추출          → 답변 작성   │
   │   요약          (답변/도구)       (예정: 시세·잔고)     + Turn 저장 │
   │   (memory 도구로                · 실행: 주문 (매수·매도,           │
   │    LLM이 판단)                   사용자 확인 후 실행)              │
   │                                · 코딩 (미구현)                   │
   └──────────────────────────────────────────────────────────┘
            │               │                    │
            ▼               ▼                    ▼
      대화 저장소       OpenRouter          NAVER·Exa(검색) · Jina·네이버 뉴스(본문)
```

Harness는 **기억하고, 판단하고, 필요하면 도구로 찾아보고, 답하는** 대화 엔진이다. 각 부분의 규칙은 아래 섹션에 있다. ① 기억은 [3](#3-context-구성과-turn-연속성)·[4](#4-compaction과-대화-보존)·[5](#5-장기-memory-관리), ② 판단은 [1](#1-harness-flow-overview)·[6.0](#60-공통-규칙), ③ 도구는 [6](#6-도구-사양), ④ 답변은 [1](#1-harness-flow-overview)·[6.1](#61-답변), 처리 중 새 메시지는 [2](#2-같은-사용자가-처리-중-새-메시지를-보낼-때)번이다.

## 1. Harness Flow Overview

모델 하나(루프 모델)가 도구를 고르고, 인자를 쓰고, 답변도 쓴다. 도구를 부르면 결과를 넣고 다시 부르며, 도구를 부르지 않고 글을 쓰면 그 글이 답변이다. Hermes Agent의 루프와 같은 방식이다.

```text
사용자 요청
    ↓
Context 구성 (→ 3, 4)
(대화 기록·Memory·이번 요청·이번에 얻은 도구 결과)
    ↓
◇ 루프 모델 호출 (등록된 도구 전체를 네이티브 도구 호출로 제공)
  │
  ├─ 도구를 부르지 않고 글을 씀 → 그 글이 답변 (Turn 종료)
  │    · 일반 질문에 답하기
  │    · 부족한 조건을 사용자에게 질문하기
  │    · 도구로 확인한 결과를 설명하기
  │    → Harness가 답변의 링크를 번호 링크로 정리 (→ 6.1)
  │    → 필요한 Memory 변경 처리 (→ 5)
  │    → 사용자에게 전달 → Turn 저장 (→ 3) → 종료
  │
  └─ 도구 호출 (한 응답에 여러 개 가능)
       · 읽기 도구 (→ 6.2)
           · 6.2.1 검색 (news_search, web_search): 한국 뉴스 기사 / 웹 페이지 후보 찾기
           · 6.2.2 본문 추출 (web_extract): 대화에 나온 링크에서 목적에 맞는 부분 (한 번에 최대 5개)
           · 6.2.3 증권사 조회 (broker): 연결 상태·시세·잔고·매수 가능
       · 실행 도구 (→ 6.4): 6.4.1 주문 (order) — 준비만 하고 확인 대기
       · 기본 도구: memory (→ 5), confirm (확인 대기가 있을 때, → 6.4)
       · 코딩 도구 (미구현, → 6.3)
       → Harness가 호출 묶음을 검사하고 실행 (→ 6.0)
       → 모든 호출에 결과를 하나씩 짝지어 Context에 추가
       → 다시 루프 모델 호출
```

- [6. 도구 사양](#6-도구-사양): 6.0 공통 규칙, 6.1 답변, 6.2 읽기, 6.3 코딩, 6.4 실행

**구현 현황**: 답변, 읽기 도구, 실행 도구(주문), memory·confirm 기본 도구가 구현되어 있다. 코딩 도구는 목표 설계다. 실행 도구는 불려도 바로 실행하지 않고 확인 대기만 만든다. 사용자가 다음 Turn에서 동의하고 모델이 그 Turn의 첫 호출로 `confirm`을 부를 때만 실행한다. 읽기 도구는 실행 확정 전에 실행되므로, 주문·취소처럼 상태를 바꾸는 작업을 읽기 도구로 등록하지 않는다.

**답변만 종료 지점**이다. 도구 결과는 모두 이번 Context에 추가하고 루프 모델이 다음을 다시 정한다. 모델은 System 지침, Memory, Summary, 이전 Turns(각 Turn의 도구 호출·결과 포함), 이번 요청, 이번 Turn의 도구 호출·결과를 모두 본다. 이번 요청 앞에는 받은 시각(`[Received 2026-09-28 14:05 KST. This is the current time, not the as-of date of any source.]`)을 붙인다. 모델은 오늘 날짜를 모르기 때문이며, 자료의 기준일로 오인하지 않도록 현재 시각임을 밝힌다. 저장되는 Turn에는 붙이지 않는다. 이번 Turn의 도구 결과는 자르지 않고 전부 준다(깊은 조사의 근거가 모두 여기에 쌓인다). 되묻기도 답변으로 하고 Turn을 끝내며, 사용자의 대답은 다음 Turn에서 이전 대화와 함께 해석된다.

Harness는 도구에 직접 요청하고 결과를 받아 다음 호출에 연결한다. PIA는 도구 요청을 매번 중계하지 않고 사용자 요청의 채널 입구와 최종 답변 전달을 맡는다. 주문 조건의 최종 검증과 처리는 pia-broker가 맡는다. **실행권 확정은 Harness 내부에서 이번 작업을 더 이상 새 메시지로 취소하지 않기로 하는 단계**이며, 사용자에게 추가 승인을 요청한다는 뜻이 아니다.

조사는 한도 중 먼저 닿는 곳에서 멈춘다: 읽기 도구 20회, 조사 시간 90초(PIA가 `research_timeout_seconds`로 바꿀 수 있음). 어느 경우든 실패로 끝내지 않고, 도구 없이 "조사가 한도로 끝났으니 지금까지의 결과로 답하고 확인하지 못한 부분을 밝히라"는 알림을 붙여 한 번 더 불러 그 답변으로 끝낸다(Hermes의 반복 예산 소진 처리와 같다). 모델 호출 자체의 장애와 주문 `confirm`은 이 경로로 바꾸지 않는다. 도구를 자동 재실행하지 않는다.

## 2. 같은 사용자가 처리 중 새 메시지를 보낼 때

```text
같은 사용자의 이전 메시지 처리 중
                ↓
          새 메시지 도착
                ↓
        ◇ 현재 처리 단계? — 코드의 if문
          ├─ 답변 생성 중
          │    → 이전 생성 취소
          │    → 미완료 입력과 새 입력을 합쳐 다시 생성
          │
          └─ 실행 확정 후 (주문의 confirm 호출 시점부터, 또는 답변 전달·저장 단계)
               → 진행 중인 작업은 마침
               → 새 메시지는 다음 작업으로 대기
```

처리 중인 작업이 없으면 바로 새 답변 생성을 시작한다. 한 사용자에게 진행 중인 답변 생성은 한 번에 하나이며, 다른 사용자들의 작업과는 별도로 관리한다. 단계 확인은 LLM이 아닌 Harness 코드가 한다.

## 3. Context 구성과 Turn 연속성

```text
새 사용자 요청
      ↓
Context 구성
  System 지침
  Memory
  Summary
  이전 완료 Turns  (사용자 요청 + 도구 호출·결과 + 최종 답변)
  이번 사용자 요청 + 이번 Turn의 도구 결과(있다면)
      ↓
모델 호출
  ├─ 도구 호출 → 결과를 이번 Context에 추가
  │                  → Context 구성으로 돌아감
  └─ 최종 답변 → 이번 Turn 저장 (사용자 요청 + 도구 호출·결과 + 최종 답변)
                  → 다음 요청의 '이전 완료 Turns'에서 읽음
                  → 크기가 기준을 넘으면 4. Compaction
```

System 지침은 host가 제공하는 규칙이다. Memory는 오래 기억할 사용자 정보, Summary는 오래된 대화의 요약이며, 둘 다 없으면 Context에서 생략한다. 이전 Turns·이번 요청·도구 결과도 모델이 참고할 데이터이지 System 지침이 아니다.

모델을 부르기 전에는 크기를 확인하지 않는다. 답변 뒤 Compaction(→ 4)이 대화를 모델 한도보다 훨씬 작게 유지하고, 그래도 한도를 넘는 요청은 모델이 거절한다(모델 오류로 끝남). 크기 판정은 코드가 하고, Summary 생성에 LLM을 사용한다.

이전 Turn은 일어난 그대로 다시 넣는다: 사용자 요청 → 그 Turn의 도구 호출과 결과(모델 응답 단위, 호출 ID로 짝) → 최종 답변. "좀 더 찾아봐", "아까 표에서 3위는?" 같은 후속 질문이 이전 조사 결과를 다시 쓸 수 있게 하기 위해서다. 매번 같은 내용을 같은 순서로 넣으므로 프롬프트 캐시도 그대로 쓰인다. 저장되는 것은 도구 결과이며 웹 페이지 원문은 아니다(→ 6.2.2). 검색 후보는 제목·날짜·링크만 저장하고 짧은 설명은 그 Turn에서만 보여준다. 검색 결과 크기의 대부분이 설명이고, 이후 Turn에서 더 필요하면 페이지를 읽는다. 본문 추출의 요약·확인된 근거는 그대로 저장한다. 완료된 Turn만 저장하므로 중간에 끊긴 호출은 남지 않는다. 저장소의 Turn 크기 한도(PIA 기본 256KiB)를 넘으면 그 Turn은 도구 기록 없이 사용자 요청과 최종 답변만 저장한다. 확인 대기 목록과 한도 알림 같은 Harness 문장은 저장하지 않는다. 답변 뒤에 Harness가 붙여 보내는 글(주문 확인 질문, Memory 결과, 확인 만료 알림)도 사용자에게만 보내고 저장하지 않는다. Turn의 답변은 모델이 쓴 답변(출처는 번호 링크)이다. 저장된 답변은 다음 Turn에 모델이 예전에 쓴 답변으로 다시 보이는데, 붙인 글까지 들어가 있으면 모델이 그 모양을 흉내 내 확인 질문을 직접 써서 두 번 나왔다(측정 2026-09-30). 주문 확정에 필요한 정보는 매 Turn의 확인 대기 알림으로 따로 들어간다.

이전 대화(Summary나 이전 Turns)가 있으면 그 뒤, 이번 요청 앞에 Harness 문장 한 줄을 넣는다: "The messages above are earlier turns, each already answered." 이전 Turn도 이번 Turn과 같은 도구 호출 형식이라, 이 줄이 없으면 이번 조사가 비었을 때 모델이 끝난 이전 질문의 조사를 이어 이전 질문에 답할 수 있다(측정에서 실제로 있었다). 이번 요청이 무엇인지는 줄 바로 아래라는 위치로 드러난다.

## 4. Compaction과 대화 보존

Turn은 한 번의 사용자 요청, 그 과정의 도구 호출·결과, 최종 답변을 묶은 기록이다. Memory는 오래 기억할 사용자 정보이고, Summary는 오래된 대화의 압축본이다. 서로 다른 데이터다.

```text
답변을 보내고 Turn을 저장한 뒤, 마지막 모델 호출의 크기를 코드로 확인
(모델이 알려 준 실제 사용량 usage.total_tokens; 없을 때만 추정치)
  ├─ 256K 토큰 미만 → 그대로 둠
  └─ 256K 이상
       ↓
    완료된 Turns를 두 그룹으로 나눔
      · 남김: 가장 최신 Turn은 반드시 유지하고,
              그 앞의 최근 Turns는 4만 자에
              들어가는 만큼 유지 (고정된 개수가 아님,
              도구 기록까지 글자 수로 셈)
      · 요약: 나머지 오래된 Turns
       ↓
    기존 Summary + 요약할 Turns(요청·답변만) → LLM이 새 Summary 생성 (2만 자 이내)
       ↓
    새 Summary가 비어 있지 않고, 2만 자 이내이고, 원본보다 짧은지 확인
       ↓
    새 Summary를 DB에 저장
      · 성공: 기존 Summary 하나를 교체한 뒤,
              새 Summary에 포함된 원본 Turns를 DB에서 삭제
      · 실패: 기존 Summary와 원본 Turns를 그대로 유지
```

답변 뒤에 하는 이유는 요약 LLM 호출을 사용자가 기다리지 않게 하기 위해서다. 실행 확정 상태에서 하므로 그동안 온 새 메시지는 기다린다. 답변 전달과 저장이 끝난 뒤라, Compaction이 실패해도 결과는 전달됨(`DELIVERED`, `compaction_failed`)이다. 기준 크기는 `CompactionPolicy`의 `trigger_tokens`(기본 256,000)다. Summary 길이는 `summary_chars`(기본 20,000자), 가장 최근 Turn 앞에 더 남기는 최근 Turns 몫은 `tail_chars`(기본 40,000자)다. 기준은 모델이 세어 주는 토큰이고, Harness가 직접 재는 두 크기는 글자 수다(Harness는 토큰을 셀 수 없다). Summary 출력 토큰 상한(`max_tokens`)은 글자 한도의 두 배로 둔다. 모델이 폭주할 때 비용·시간을 막는 여유 있는 상한일 뿐 2만 자를 보장하지는 않는다(한국어는 한 글자가 여러 토큰일 수 있다). 출력이 잘리면 Compaction이 실패하고 기존 Summary와 Turns는 그대로 남는다. 실제 출력 토큰은 측정에서 확인한다. 압축 직후 Context는 시스템 지침·도구 정의(약 6천 자) + Memory(목표 2천 자) + Summary(최대 2만 자) + 최근 Turns로, 기준의 약 10~20%에서 다시 시작한다. 모델 한도의 비율이 아니라 크기로 정한다. 모델 한도(luna 105만 토큰)는 매 Turn 다시 보낼 만한 크기보다 훨씬 크고, Context가 클수록 매 호출이 전체를 다시 읽어 느려지고 비싸지기 때문이다. `ModelTokenBudget`의 `context_limit`은 모델의 실제 한도로 둔다. `trigger_tokens`가 입력 예산(한도에서 답변용 예약을 뺀 값) 이상이면 설정 오류다.

모델을 부르기 전에는 크기를 확인하지도 압축하지도 않는다. 예전에는 호출 직전에 요청을 UTF-8 바이트로 세어 같은 256K 기준과 비교했는데, 바이트는 실제 토큰의 서너 배라 실제로는 훨씬 작은 대화를 Turn 도중에 사용자를 기다리게 하며 압축했다(측정 2026-09-30). 256K에서 압축하면 모델 한도(105만)까지 약 75%가 남으므로 답변 뒤 확인으로 충분하다. 알려진 한계: 답변 뒤 Compaction이 계속 실패해 대화가 모델 한도를 넘으면 모델이 요청을 거절해 Turn이 모델 오류로 끝나고, 답변이 없으니 Compaction도 돌지 않는다. 그 전에 `compaction_failed`가 여러 번 보고되므로 host가 알아챈다.

Summary는 세션마다 현재본 **하나**를 저장한다. 다음 Compaction은 이전 Summary와 새로 오래어진 Turns를 합쳐 새 Summary로 **교체**하며, 과거 Summary 버전을 쌓지 않는다. 요약에 포함된 원본 Turns는 새 Summary 저장 성공 후 삭제되므로, Summary에 담기지 않은 오래된 세부사항은 복원할 수 없다.

최근 Turns는 4만 자라는 크기 몫으로 선택하므로 남는 **개수는 일정하지 않다**. 요약되지 않은 Turn은 PIA가 정한 보존기간(기본 30일)의 적용을 받고, 요약된 Turn은 그보다 일찍 삭제된다. 따라서 DB에는 장기 Memory, 세션의 현재 Summary, 남겨 둔 원본 Turns가 주로 남으며 **전체 대화 원문 이력을 보관하는 구조가 아니다**. 장기 Memory는 Compaction이 직접 삭제하지 않는다. 이번 요청과 아직 끝나지 않은 도구 사용은 오래된 완료 Turns를 고르는 대상이 아니다.

## 5. 장기 Memory 관리

Turn은 한 번의 대화 기록이고 Summary는 오래된 대화의 요약이다. **Memory는 이후 대화에 오래 도움이 될 사용자 정보를 담는 별도 문서**로, 사용자마다 현재본 하나만 두며 최대 4,000자다. 내용을 바꿀 때는 문서 전체를 교체하고 과거 버전을 쌓지 않는다.

```text
사용자 요청 처리 중 루프 모델이 memory 도구를 부름
  · 사용자가 "기억해줘 / 일부 잊어줘"라고 요청
  · 또는 오래 유지될 사실·선호를 말함 (투자 목표, 위험 성향, 보유 계획 등)
  → 도구는 신호만 기록 (update / forget)
                    ↓
답변이 확정된 뒤
       PIA의 금융 투자용 Memory 지침
       + 현재 Memory 문서 + Summary + 마지막 반영 뒤의 대화 + 이번 요청
                    ↓
       LLM이 새 Memory 문서 전체 작성 (바뀔 게 없으면 유지)
       → 2,000자 안팎을 목표로 씀 (넘으면 합치거나 덜 중요한 것을 뺌)
       → 새 문서를 작성한 경우에만 최대 4,000자인지 검증 후 교체
                    ↓
       마지막으로 반영한 대화 위치를 함께 저장
```

PIA는 “금융 투자 에이전트가 장기적으로 기억할 내용”을 정한 Memory 지침을 Harness에 반드시 전달한다. 범용 Harness에는 금융 투자용 지침을 고정하지 않는다. **무엇을 기억할지는 루프 모델이 판단한다**(Hermes 방식). 명시적 요청뿐 아니라 지나가듯 말한 오래 갈 사실도 모델이 `memory` 도구로 알린다. 시간이 지나면 도는 검토나 Compaction 직전 검토는 두지 않는다. 오래된 대화의 요점은 Summary에 남고, Memory를 고쳐 쓸 때 Summary도 함께 준다. 그래서 Compaction 뒤에 "전에 말한 것 기억해줘"라고 해도 근거를 찾을 수 있다(→ 4). 도구는 바로 쓰지 않고 신호만 기록하며, 답변이 확정된 뒤 이번 요청을 근거로 Memory 문서를 고쳐 쓴다. 새 메시지로 취소될 수 있는 생성 중에는 영속 변경을 하지 않기 위해서다. 모델이 부른 요청은 조사가 한도로 끝난 Turn에서도 반영한다. 일반 답변 작성과 Memory 문서 작성은 별도 LLM 호출이다.

의미 있는 Memory 변경은 별도 알림 대신 일반 답변 끝에 최대 3개(각 200자 이하) 안내한다. Memory 반영이 실패하면 답변에서 알린다.

`forget`은 사용자가 지정한 내용을 지우는 기능이다. 지정한 내용이 Memory의 마지막 항목이면 문서가 비워질 수 있다. 대화 문맥 전체를 초기화하는 별도 기능은 제공하지 않는다.

## 6. 도구 사양

루프 모델이 부르는 도구의 동작을 이곳에 모은다. 도구는 대분류(답변·읽기·코딩·실행)로 나누며, 실행 뒤 동작·한도·실패 규칙은 대분류가 정한다.

### 6.0 공통 규칙

도구 하나는 이름, 설명(모델이 언제·어떻게 쓰는지), 인자 스키마, 실행 함수를 갖는다. 도구의 설명과 도구 안에서 쓰는 프롬프트는 그 도구 파일에 둔다(예: `web_extract.py`). 모델 어댑터는 호출만 한다. 결과가 길어 정리가 필요한 도구만 도구 안에서 정리 LLM을 부른다(지금은 본문 추출).

| 대분류 | 도구 | 실행 뒤 | 한도·실패 |
|---|---|---|---|
| 답변 | (도구 호출 없는 응답) | Turn 끝 | 번호 링크 정리 |
| 읽기 | `news_search`, `web_search`, `web_extract`, `broker` | 결과를 넣고 모델을 다시 부름 | 20회·90초, 동시 3개. 예상 가능한 실패는 결과 문장, 코드 오류는 `TOOL_FAILED` |
| 코딩 | (미구현) | — | — |
| 실행 | `order` | 준비 뒤 도구 없이 답변을 받음 | 확인 대기, 한 번에 5건까지 |
| 기본 | `memory`, `confirm` | 계속 / 실행 뒤 답변 | Harness가 정의, PIA가 등록하거나 뺄 수 없음 |

**한 응답의 호출 묶음은 실행 전에 전체를 검사한다.**

- 인자가 JSON 객체가 아니거나, 읽기 도구의 필수 인자가 비었거나, 없는 도구 이름이거나, `memory`의 `action` 값이 틀리면 도구를 부르지 않거나 준비하지 않고 그 이유를 결과로 돌려준다. 도구 고유의 값 검사(예: 주문의 `side`)는 도구가 준비 단계에서 하고 같은 방식으로 이유를 돌려준다. 모델이 고쳐 다시 부른다(Hermes와 같음).
- `confirm`이 있는 묶음에서는 `confirm`만 실행하고, 나머지 호출에는 "확정이 먼저, 결과를 본 뒤 다시"를 결과로 붙인다.
- 실행 도구 호출은 묶음당 5개까지 준비하고, 넘는 호출에는 그 사실을 결과로 붙인다.
- 읽기 호출은 남은 한도(20회 중)까지만 실행하고, 넘는 호출에는 "한도에 닿음"을 붙인 뒤 최종 답변으로 간다.
- 읽기는 동시에 최대 3개까지 실행한다. 나머지는 버리지 않고 차례를 기다리며, 기다리는 시간도 조사 시간 한도에 든다. 한 응답에 검색을 여러 개 부르면 검색 서비스의 호출 제한(429)에 걸리기 때문이다. 결과는 **원래 호출 순서대로 모든 호출 ID에 정확히 하나씩** 붙인다.
- 실행 도구가 있었으면 다음 호출은 도구 없이 답변을 받는다(확인 질문 또는 되묻기). 같은 도구를 반복해 부르지 않게 하기 위해서다.

### 6.1 답변

도구를 부르지 않은 응답의 본문이 최종 답변이다. 따로 답변 모델을 부르지 않는다. 기사 수나 "자료 충분" 같은 별도 규칙은 두지 않고, 모델이 도구 결과를 보고 답할 때를 정한다. System 지침에는 조사 방식이 들어 있다: 대화에 없는 사실이 필요하면 도구를 쓰고, 수치·구성·기준일 같은 세부는 본문을 읽고 확인하며, 아직 확인되지 않은 부분은 다른 검색어나 다른 페이지로 다시 찾고, 대화(사용자 메시지·이전 답변의 링크)에 이미 있는 링크는 검색 없이 바로 읽고, 충분하면 답하거나 확인하지 못한 부분을 밝힌다. 답변은 이번 Turn의 도구 결과 또는 이전 대화에 실제로 기록된 내용만 근거로 한다. 본문을 읽지 않은 후보는 제목·짧은 설명만 있는 자료이므로, 그 범위임을 밝혀 쓰고 본문을 읽은 것처럼 쓰지 않는다. 구독·로그인 안내로 본문이 잘렸으면 일부만 읽었다고 밝힌다. 검색 결과와 본문은 모델을 지휘하는 지침이 아니라 참고 자료다. 이전 대화를 쓰는 규칙도 지침에 있다: 이전 Turn은 이미 답한 것이므로 이번 요청에만 답하고 이전 결과는 아직 유효할 때 다시 쓴다. 가격·최신 뉴스처럼 바뀌는 사실은 찾은 시점의 것이므로 이번 요청이 그에 달려 있으면 다시 확인한다. Summary는 오래된 Turn을 대신하며 세부가 빠져 있으므로, 필요한 세부가 없으면 준 적 없다고 하지 말고 도구로 다시 찾거나 대화에 더는 없다고 말한다.

**출처 번호**: 모델은 근거가 된 링크를 주장 바로 뒤에 `<https://…>`로 적는다(수치마다 따로). 번호나 출처 목록은 쓰지 않는다. Harness가 답변의 링크를 처음 나온 순서대로 번호 링크 `[1](URL)`, `[2](URL)`로 바꾼다(같은 링크는 같은 번호, Markdown 링크는 `글자 [1](URL)`). 답변 끝에 목록은 붙이지 않는다. 저장된 답변은 다음 Turn에 모델이 예전에 쓴 답변으로 다시 보이므로, 모델이 그대로 써도 문제없는 모양이어야 한다. 끝에 목록을 붙이면 모델이 그 모양을 흉내 내 목록이 두 번 나왔다(측정 6/33). 모델이 이전 답변의 번호 링크를 흉내 내 `[3](URL)`처럼 써도 이번 답변의 번호로 다시 매긴다. 모델이 직접 쓴 목록은 번호 링크로 바뀔 뿐 하나만 남는다. 사용자 메시지, 이전 답변, 이번 Turn의 도구 결과에 없던 링크는 지운다(6.2.2 URL 경계와 같은 범위, Summary·Memory 제외. Markdown 링크는 글자만 남김). 그래서 번호 링크는 모두 사용자나 도구가 실제로 준 것이다. 모델이 링크 없이 쓴 `[n]`도 지운다(`items[1]` 같은 색인은 두고). 가리키는 링크가 없기 때문이다. 코드 블록·인라인 코드는 바꾸지 않고, 지운 자리 옆 공백만 정리한다. 지우고 나서 본문이 비면 원문으로 되돌리지 않고 답변 생성 실패로 처리한다. 번호 링크는 답변과 함께 Turn에 저장되므로 다음 Turn에서도 링크를 다시 읽을 수 있다. 번호 링크는 링크가 어디서 왔는지 확인한 것이지, 그 페이지를 읽었거나 주장을 뒷받침한다는 뜻은 아니다(읽지 못한 링크도 들어갈 수 있다). 어느 수치에 어느 번호를 붙일지는 모델이 정하므로, 번호를 잘못 붙이는 것까지는 막지 못한다. 괄호가 든 URL은 괄호 앞까지만 링크로 인식한다(URL 경계와 같은 규칙).

답변은 Markdown이다(번호 링크, 굵게 등). 채널에 맞게 보여주는 것은 host 몫이다. PIA는 Telegram으로 보낼 때 번호 링크를 `<a href>`로, 굵게를 `<b>`로 바꾸고 나머지 글자는 HTML escape하며, 긴 답변은 원문을 줄·공백 경계로 먼저 나눈 뒤 조각마다 바꾸므로 링크·태그가 잘리지 않는다(링크에는 공백이 없다). 굵게 표시가 조각 경계에 걸리면 그 별표는 글자로 남는다(Telegram 4,096자 한도는 서식 해석 뒤 기준).

### 6.2 읽기 도구

읽기 도구는 외부 자료나 현재 상태를 가져오며, 그 자체로 주문 같은 상태 변경을 하지 않는다. 예상 가능한 실패(연결·한도·오류 응답)는 결과 문장으로 돌려주고, 코드 오류는 Turn을 끝낸다.

읽기 도구의 호출과 결과(검색어·후보의 제목·날짜·링크, 본문 추출의 요약·근거)는 Turn과 함께 저장되어 다음 Turn에서도 보인다(→ 3). 그보다 자세한 내용이 필요하면 링크를 다시 읽거나 다시 검색한다. 반복 탐색은 1번의 세 한도가 제한한다.

OpenRouter 내장 Web Search는 사용하지 않는다. 검색은 `news_search`(한국 뉴스)와 `web_search`(웹 전체), 페이지 내용은 `web_extract`로만 한다. 어느 검색을 쓸지는 모델이 도구 설명을 보고 고른다. 한 도구가 실패했을 때 다른 공급자로 자동으로 넘기는 대체 경로는 두지 않는다.

#### 6.2.1 검색

뉴스 검색(`news_search`)은 한국 뉴스 기사 후보를 찾는 읽기 도구다. 공급자는 NAVER API HUB 뉴스 검색이고, host가 준 키(Client ID·Secret)를 헤더로 보낸다. 키는 필수다. PIA는 자기 비밀 저장소에서 읽어 `NaverNewsSearch(client_id=..., client_secret=...)`로 넘긴다. NAVER API HUB는 지금 한시적으로 무료이고, 검색 호출은 월 775,000회가 한도다(유료로 바뀌면 미리 공지된다). 한 번에 관련도순으로 5건을 받고, 후보마다 제목·날짜·짧은 설명·링크가 있다. 링크는 네이버 뉴스 주소(`*.news.naver.com`)가 있으면 그것을, 없으면 언론사 원문 주소를 쓴다. 그중 `n.news.naver.com` 기사는 본문 추출이 직접 읽고, 스포츠·연예 주소는 Jina로 읽는다(6.2.2). 회사·펀드 페이지, ETF 구성, 공시, 해외 자료, `site:` 검색은 웹 검색의 몫이다. 두 도구의 설명에 이 구분을 적는다.

웹 검색(`web_search`)은 뉴스를 포함한 웹 전체에서 후보를 찾는 읽기 도구다. 공급자는 Exa의 MCP 서버(`web_search_exa`)이고, host가 준 Exa 키를 `x-api-key` 헤더로 보낸다(URL에는 넣지 않는다). 키는 필수다. 키 없는 호출은 여러 사용자가 한 한도를 나눠 써서 조사 중 429로 막혔다(측정 2026-09-30). PIA는 OpenRouter 키처럼 자기 비밀 저장소에서 읽어 `ExaWebSearch(api_key=...)`로 넘긴다. 검색 한 번에 후보를 최대 5건 받으며, 후보에는 본문이 없다. 본문이 필요하면 모델이 6.2.2 본문 추출을 따로 부른다.

```text
◇ 모델이 web_search 호출 (검색어를 씀)
  · 앞선 결과에서 아직 확인되지 않은 부분을 찾음
  · site:example.com, "정확한 구문" 같은 연산자 사용 가능
    ↓
Harness가 Exa MCP를 1회 호출 (numResults=5)
    ↓
후보 최대 5건
  · 제목·링크·날짜(있으면)·짧은 발췌 (본문 없음)
  · 이번 Turn에서 이미 받은 링크는 제외
    ↓
검색어와 후보를 이번 Turn의 Context에 추가
    ↓
◇ 모델이 다시 판단
  ├─ 더 찾을 필요가 있음 → web_search (다른 검색어)
  ├─ 페이지 안의 내용이 필요함 → web_extract
  └─ 답변하기에 충분함 → 답변
```

MCP 응답은 결과를 합친 텍스트다. `---`로 나뉜 블록마다 `Title:`, `URL:`, `Published:`, `Highlights:` 뒤를 읽고, URL이 없는 블록은 버린다. 텍스트가 있는데 후보를 하나도 읽지 못하면 "검색 결과를 해석하지 못함"을 글자 수와 함께 결과로 돌려준다. 응답에는 검색어·본문이 들어 있을 수 있어 내용은 적지 않는다. HTTP 오류·한도 초과·오류 응답도 결과 문장으로 돌려주며, 코드 오류만 Turn을 끝낸다. 후보의 날짜가 Context에 함께 들어가므로 최신성은 모델이 날짜를 보고 판단한다.

#### 6.2.2 본문 추출

본문 추출(`web_extract`)은 **대화에 나온 URL**의 페이지를 읽고, 목적(goal)에 맞는 **요약과 원문 근거**를 가져오는 읽기 도구다. 사용자 메시지, 이전 답변, 이전 Turn과 이번 Turn의 도구 결과(검색 후보, 본문 추출의 확인된 근거)에 있는 링크(Markdown 링크 포함)를 읽을 수 있다. 근거에 적힌 링크는 페이지에 실제로 있던 것이라, 기사에 걸린 공식 페이지를 따라가는 데 쓸 수 있다. 같은 링크를 같은 목적으로는 한 Turn에 한 번만 읽는다(몇 초 안에 같은 페이지를 다시 읽어도 결과는 같다). 목적(goal)이 다르면 다시 읽는다. 요약이 놓친 것을 다른 목적으로 다시 찾을 수 있게 하기 위해서다. Summary와 Memory는 모델이 쓴 글이라 대상에서 뺀다.

```text
◇ 모델이 web_extract 호출 { urls: [1~5개], goal: 찾을 내용 }
  · 대화에 나온 링크를 그대로 복사
    ↓
Harness가 URL마다 (동시에)
  ├─ 대화에 없는 URL → 읽지 않음 (결과에 URL을 다시 적지 않음)
  ├─ 이번 Turn에 같은 목적으로 이미 읽은 URL → 다시 읽지 않음
  └─ 그 밖 → 페이지 받기 → 앞 30,000자 → 요약 LLM(goal·사용자 요청·페이지만 봄) → 근거 원문 대조
       · 네이버 뉴스 기사(n.news.naver.com/…/article/…): 직접 받아 본문 영역·제목·날짜만
       · 그 밖, 또는 본문 영역이 없는 기사: Jina Reader (링크 URL·이미지 제거)
    ↓
URL별 상태 줄 + 페이지별 요약·검증된 근거(합계 약 2,000자)를 이번 Turn의 Context에 추가 (원문은 넣지 않음)
    ↓
◇ 모델이 다시 판단
```

- **뒤에 정리**: 페이지 원문은 Context에 넣지 않는다. 넣으면 이후 모든 모델 호출이 수만 자를 매번 다시 읽는다. 뒤 단계 LLM은 goal, 이번 사용자 요청, 페이지만 받고 요약(goal 기준 정리, 페이지에 없는 것 포함)과 근거(원문 그대로 복사한 구절)를 돌려준다. 요약의 링크는 지운다. 수치·날짜는 근거에서만 인용하도록 결과 머리말에 적는다. 출력이 잘리면 모델 어댑터가 재시도하도록 설정된 경우(`max_attempts` 2 이상, 기본 1)에만 다시 시도한다.
- **원문 대조**: 근거 구절마다 페이지(링크 URL을 뺀 앞 30,000자)에 실제로 있는지 코드가 확인한다. 공백 차이만 무시한다. 없는 구절만 빼고 나머지는 쓴다. 바뀐 수치나 지어낸 링크가 답변과 읽기 허용 목록에 들어가지 않게 하기 위해서다. 확인된 근거가 하나도 없으면 요약도 싣지 않는다. 요약은 모델이 쓴 글이라 근거 없이는 증거가 아니기 때문이다. Markdown 링크의 URL은 이미 지웠으므로, 결과에 남는 링크는 페이지 본문에 그대로 적힌 URL이 확인된 근거에 들어 있을 때뿐이다.
- **URL 경계**: 대화에 실제로 나온 링크만 읽는다. 이 규칙은 도구가 아니라 Harness의 읽기 대분류 규칙이다. 도구가 `url_argument`(여기서는 `urls`)를 선언하면 Harness가 대화(사용자 메시지·저장된 답변·저장된 도구 결과·이번 Turn 도구 결과)에 없는 링크와 이번 Turn에 같은 목적(링크를 뺀 나머지 인자)으로 이미 읽은 링크를 걸러 도구를 부르고, 읽을 것이 없으면 도구를 부르지 않고 "새로 읽을 링크 없음"을 결과로 돌려준다. 같은 응답의 두 호출이 같은 링크를 요청해도 한 번만 읽는다. 악의적인 페이지가 사용자 정보를 담은 새 URL을 만들게 유도해도, 그 URL은 대화에 없으므로 읽지 않는다. 거부한 URL은 결과에 다시 적지 않는다. 결과에 적힌 링크는 다음 호출에서 읽을 수 있게 되기 때문이다.
- **상태 줄**: 읽음(근거 N개, 페이지에 없어 뺀 수, 앞 30,000자만 읽음) / 읽었지만 확인된 근거 없음(인용할 것 없음) / 목적에 맞는 내용 없음 / 앞 30,000자에서 찾지 못함(나머지는 확인 못 함) / 읽지 못함 / 이미 읽음(개수만). 잘린 페이지는 "없음"이라고 단정하지 않는다.
- **실패**: 페이지를 받지 못함(연결·상태 코드·빈 응답), 링크·이미지를 빼니 글자가 없음, 이 페이지 때문에 난 요약 LLM 실패(출력 잘림·형식 오류·거절)는 `PageReadError`로 "읽지 못함" 결과가 된다. 그 밖의 오류는 Turn을 끝낸다. 코드 오류, 그리고 키·권한·공급자 장애처럼 모든 페이지에 똑같이 생길 오류다. 깨진 도구를 모델이 모른 채 계속 부르지 않게 하기 위해서다(6.2.1과 같은 규칙).
- **공급자**: Jina Reader(`POST https://r.jina.ai/`)를 키 없이 부른다. `DNT: 1`로 캐시·기록을 막는다. 키를 쓸 때는 `Authorization` 헤더를 붙인다. 네이버 뉴스 기사(`https://n.news.naver.com/…/article/…`)만 우리 서버가 직접 받는다. 기사 페이지가 완성된 HTML로 오고 본문이 정해진 요소(`<article id="dic_area">`)에 있어서, 파이썬 기본 파서로 그 요소와 제목·기사 날짜만 꺼낸다(메뉴·광고·관련 기사·댓글은 들어가지 않는다). Jina를 한 번 덜 거치고 Jina의 키 없는 분당 한도(20회)도 아낀다. 이 경로도 redirect는 따르지 않으며, 받지 못하거나 본문 요소가 없으면(구조 변경, 삭제된 기사) 그 링크는 Jina로 읽는다. 스포츠·연예 기사는 다른 주소에서 스크립트로 그려지므로 Jina로 간다. 그 밖의 주소에 우리 서버가 직접 접속하는 일은 없다.

#### 6.2.3 증권사 조회

증권사 조회(`broker`)는 사용자가 연결한 증권 계좌로 연결 상태·시세·잔고·매수 가능을 조회하는 읽기 도구다. 주문 도구와 같은 Broker 내부 경로를 쓰고, PIA가 넘긴 서명된 client를 같이 쓴다(`BrokerReadTool(base_url=..., client=...)`). harness는 AWS를 모른다.

```text
◇ 모델이 broker 호출 { action, name(시세·매수 가능만) }
  ├─ status  → Broker 연결 상태
  ├─ quote   → 종목 찾기 → 현재가·전일 대비·등락률·거래량·거래대금·시가총액·PER·PBR·52주 최고·최저
  ├─ account → 보유 종목(매도 가능 수량 포함)·예수금·D+2 예수금·총평가·총손익
  └─ buyable → 종목 찾기 → 증권사가 계산한 미수 없는 매수 가능 금액·수량 (시장가 기준)
    ↓
조회 시각(KST)을 붙인 결과 문장을 이번 Turn의 Context에 추가
```

- **계산하지 않는다**: 매수 가능 수량은 증권사 값(KIS 매수 가능 조회, 시장가 기준, 미수 없음)만 쓴다. 예수금÷가격은 결제 대기·미체결 주문·증거금률·시장가 상한가 기준 때문에 실제와 다를 수 있다. 도구 설명과 `account` 결과에 "매수 가능은 buyable로"를 적는다.
- **부호**: 전일 대비·손익·수익률은 하락·손실이면 음수로 보여 준다.
- **종목 찾기**: 주문 도구와 같은 `/internal/instruments`를 쓴다(`broker_instruments.py`). 여러 후보면 이름을 보여 주고 묻게, 없으면 정식 종목명을 묻게 한다.
- **실패**: Broker 409는 "쓸 수 있는 확인된 KIS 연결이 없음"으로 알린다. 다른 증권사 연결만 있어도 409이므로 "연결 안 됨"이라고 단정하지 않는다. 503·그 밖의 상태·무응답·해석할 수 없는 응답도 결과 문장이다. 한 번의 Broker 문제로 Turn을 끝내지 않는다. 다시 시도하지 않는다.
- **최신성**: 결과에 조회 시각을 붙인다. 저장된 지난 Turn의 시세·잔고는 그때 값이므로 나중 질문에는 다시 조회한다(도구 설명과 AGENT_INSTRUCTION).
- **데이터**: 결과에 계좌번호·자격 증명은 없다. `account`는 예수금만 물어도 보유 종목 전체를 돌려주고, 그 결과가 Turn 도구 기록으로 저장된다.

### 6.3 코딩 도구

미구현이다. 자료 정렬·계산·분석용 일회성 코드를 격리 실행하는 도구를 목표로 한다. 추가할 때 이 대분류의 한도·실패 규칙을 정한다.

### 6.4 실행 도구

실행 도구는 주문처럼 상태를 바꾸는 도구다. **항상 사용자 확인을 받는다.** 도구가 불리면 실행하지 않고 확인 대기를 만들며, 다음 Turn에서 사용자가 동의할 때만 실행한다. 확인도 모델이 기본 도구 `confirm`으로 처리한다(Hermes처럼 도구로, 버튼 없이).

```text
[Turn 1] ◇ 모델이 실행 도구 호출 (주문 여러 건이면 여러 번, 최대 5건)
    ↓
도구가 준비
  ├─ 부족·모호 → 도구 결과 "무엇이 필요한지" → 도구 없이 답변(되묻기) → 종료
  └─ 준비됨 → 도구 결과 "확인 대기 (action ID a12)"
    ↓
도구 없이 답변 → 답변 맨 끝에 도구가 만든 확인 문장(건마다) → 전달된 뒤 확인 대기 저장 → 종료

[Turn 2] ◇ 확인 대기가 있고 5분 이내인가?
  ├─ 5분 지남 → 버리고 답변 끝에 "확인 시간이 지났습니다. 다시 요청해 주세요."
  └─ 이내 → Context에 "확인 대기: ID — 요약" 목록, 도구에 confirm 추가
            ├─ 첫 호출이 confirm {action_ids} → 실행 확정 → 고른 대기를 그대로 실행 → 결과로 도구 없이 답변
            ├─ 같은 도구 → 조건 변경("28만원에") → 새 확인 대기
            └─ 그 밖     → 일반 처리
    ↓
답변이 전달되면 확인 대기는 쓰였든 아니든 버림 (새로 만든 것만 남음)
```

- **`confirm`은 그 Turn의 첫 모델 응답에서만 실행한다.** 검색 결과나 페이지 같은 외부 자료가 Context에 들어온 뒤의 `confirm`은 실행하지 않고 "확정은 다른 도구보다 먼저"를 결과로 돌려준다. 첫 응답 때 모델이 읽은 것은 사용자 메시지와 이전 대화뿐이라, 페이지 속 문장에 속아 주문을 확정하는 경로가 막힌다. 동의는 사용자에게서 와야 한다는 경계를 코드 규칙 하나로 지킨다.
- `confirm`은 모든 실행 도구가 함께 쓰는 기본 도구다. 모델이 사용자 메시지("응", "삼성만 해줘")를 보고 확정할 대기의 ID를 고른다. 없는 ID면 아무것도 실행하지 않는다.
- `confirm`이 불리면 Harness가 실행을 확정한다(→ 2). 이때부터 새 메시지는 기다리고, 조사 시간 제한은 적용하지 않는다. 저장된 요청을 다시 작성하지 않고 그대로 실행하며, 결과를 Context에 넣고 도구 없이 답변을 받는다.
- 확인 대기는 사용자당 최대 5건이며 Harness 메모리에만 둔다. Bot이 재시작되면 사라지고, 사용자가 다시 요청하면 된다.
- `confirm` Turn의 Memory는 바꾸지 않는다(첫 응답이 `confirm`이면 같은 응답의 다른 호출은 실행하지 않는다).
- 확인 문장은 LLM이 아니라 도구가 인자로 만든다. Harness가 답변 맨 끝에 따로 붙여 사용자에게 보내고, Turn에는 저장하지 않는다(→ 3). 다음 Turn의 모델은 확인할 주문을 확인 대기 알림으로 받는다. Memory 안내 목록과 달리 개수 제한으로 밀려나지 않는다.
- 되묻기도 답변으로 Turn을 끝낸다. 사용자의 대답("10주", "응")은 다음 Turn에서 이전 대화와 함께 해석한다. 모호한 종목 후보 같은 도구 결과도 Turn에 저장되어 다음 Turn에서 보인다.
- 실행 뒤 답변 생성이 실패하면 LLM 없이 도구의 고정 결과 문장을 보낸다. 실행 함수는 요청을 보낸 뒤에는 예외를 내지 않고 결과 문장을 돌려준다.

#### 6.4.1 주문

pia-broker의 내부 경로로 한국 주식을 매수·매도한다. Harness는 AWS를 모르며, PIA가 Broker 주소와 요청 서명(httpx auth)을 넘겨준다. 회원 ID는 `user_key`다.

```text
◇ 모델이 order 호출 { name, side, quantity, order_type(기본 LIMIT), price }
  · name은 공식 종목명(삼전 → 삼성전자, 하닉 → SK하이닉스). 사용자가 코드를 말했을 때만 코드
  · 대화 전체에서 채움 ("3주" 같은 짧은 대답은 직전 주문 요청을 이어감)
  · 매수/매도·수량·가격은 지어내지 않고, 말하지 않았으면 null
    ↓
◇ name · side · quantity가 있나? 없으면 "부족한 인자" → 되묻기
    ↓
Broker 종목 찾기
  ├─ AMBIGUOUS → 후보 목록 → 되묻기 (답변에 후보 이름을 적음)
  ├─ NOT_FOUND → 공식 종목명을 되묻기
  └─ FOUND
    ↓
Broker 현재가 (계좌 미연결이면 "Member Web에서 연결·확인 필요" → 답변)
  · 지정가인데 가격이 없으면 현재가
    ↓
확인 대기 { 주문 내용, request_id(새로 만듦) }
확인 문장:
  "삼성전자(005930) 10주를 285,500원 지정가로 매수할까요? (09:31 기준 현재가 285,500원)"
  "삼성전자(005930) 10주를 시장가로 매수할까요? (예상 금액 약 2,855,000원, 09:31 기준 현재가 285,500원)"
```

- 지정가가 기본이고, 시장가는 사용자가 요청할 때만 쓴다.
- 실행 결과 문장:
  - ACCEPTED: "주문이 접수되었습니다: 요약 (주문번호 …). 체결 여부는 증권사 앱에서 확인해 주세요."
  - REJECTED: "주문이 거부되었습니다: 요약. 사유: KIS 거부 문구(없으면 code)"
  - 그 밖(UNKNOWN, 응답 오류, 통신 실패): "주문 결과를 확인하지 못했습니다: 요약. 주문이 들어갔을 수 있으니 다시 주문하기 전에 증권사 앱에서 꼭 확인해 주세요." 자동으로 다시 보내지 않는다.
- 같은 확인 대기를 두 번 실행해도 같은 `request_id`라 Broker가 한 번만 주문한다.
- 범위는 매수·매도다. 취소·체결 조회·잔고는 나중에 한다.

## 기타: 지원 계약

아래 항목은 위 대화 흐름을 새로 나누지 않는 기본 계약이다.

- Harness는 모델 응답을 검증하고 실패 단계를 구분해 PIA에 알린다. 모델 요청의 재시도는 제한적이며, 실패한 도구를 Harness가 자동으로 다시 실행하지 않는다.
- 모델 호출이 실패하면(재시도 뒤에도) 답변을 지어내지 않고 실패 상태를 PIA에 전달한다.
- Harness는 등록된 도구의 입력을 확인하고 도구 API를 직접 호출한다. pia-broker는 계좌 연결·중복 주문 방지 등 주문 처리 규칙을 최종 확인한다(금액 한도는 두지 않는다). 알려진 실패나 결과 미확정도 Harness가 도구 결과로 다뤄 모델의 다음 판단에 제공한다.
- 저장소는 사용자별 데이터 분리, Turn 순서·만료, 조건부 갱신을 지킨다. 회원 상태에 따른 대화 중단과 계정 데이터 삭제는 PIA가 맡는다.
- 진행 중이라는 안내와 오류 문구를 사용자 채널에 어떻게 보여줄지는 PIA가 정한다. Harness는 필요한 결과 상태와 선택적 진행 신호만 전달한다.
- 진행 신호: 모델이 도구를 부를 때마다 `ConversationStep(next_action=도구 이름, arguments_json)`을 보낸다(실행 전). 부른 것일 뿐 실행 결과가 아니다(`confirm`을 불러도 새 메시지로 취소될 수 있다). 답변에는 신호를 보내지 않는다. 단계를 하나라도 보냈으면 Turn 끝에 `None`을 보낸다. 신호는 최선 노력이라 실패하거나 5초를 넘겨도 Turn은 계속된다. Harness는 로그를 남기지 않는다.
