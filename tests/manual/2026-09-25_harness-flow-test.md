# Harness 1번 흐름 실제 테스트 (2026-09-25)

README 1번 흐름(Jev 선택 → 읽기 도구 → 답변)이 실제 모델·API에서 설계대로 동작하는지 확인한 일회성 수동 테스트 기록이다. 자동 테스트가 아니며, 같은 시나리오를 다시 돌릴 때 비교 기준으로 쓴다.

## 구성

| 항목 | 값 |
|---|---|
| Harness | `codex/search-relevance-only` 브랜치 (main `d1e2124` 기준) |
| Jev | OpenRouter Decisions API, `~typesafe/jev-latest` (응답 모델 `typesafe/jev-1.13`) |
| 답변·검색어·Memory LLM | OpenRouter `openai/gpt-6-luna`, context 1,050,000 / 응답 4,096 |
| Search | NAVER API HUB 뉴스 검색 (실제 키, Secrets Manager `pia/dev/naver-api-hub`) |
| 본문 읽기 | 실제 기사 URL |
| 저장소 | `InMemoryConversationStore` (한 사용자의 연속 대화, 시나리오 순서대로 진행) |
| 실행 | EC2에서 일회성 스크립트로 `ConversationOrchestrator.submit`을 호출하고 Jev·도구 호출을 감싸서 기록. 스크립트는 저장소에 두지 않음 |

시스템 프롬프트와 Memory 지침은 테스트용 짧은 문장을 썼다. 따라서 "무엇을 할 수 있는지" 같은 답변의 기능 설명은 실제 PIA 프롬프트와 다를 수 있다.

## 시나리오별 기록

### 1. 일반 대화

- 질문: "안녕, 뭐 할 수 있어?"
- 흐름: Jev answer 1.0 (memory NONE) → 답변. 3.3초.
- Jev 입력: `CURRENT_USER`만, 522 토큰.
- 관찰: 답변이 아직 없는 기능(공시 요약 등)까지 언급했다. 테스트 프롬프트가 사용 가능한 도구를 알려주지 않아서이며, PIA 시스템 프롬프트에서 다룬다.

### 2. 최신 뉴스 질문

- 질문: "오늘 삼성전자 관련 주요 뉴스 알려줘"

  - Jev read:c1 (0.49) → answer (0.46 vs read:c2 0.34). 기사 1건(성과급 기부 인터뷰)으로 답함.
  - 기사 1건 본문(6,000자)으로 Jev 입력이 1,740 → 6,160 토큰.
- 수정 (`5ba1ab2`): 정렬은 항상 관련성순(sim), 검색어는 대상 이름 위주로 쓰고 "뉴스·최근·오늘·주요" 같은 일반어는 넣지 않음.
- 2차:
  - 검색 두 번("삼성전자 반도체 실적", "삼성전자 갤럭시 스마트폰") → 후보 10건 모두 삼성전자가 중심인 9/24~25 기사.

- 결정 (`0194dcf`): 읽지 않은 후보도 범위(제목·요약)를 밝히면 근거로 쓸 수 있다. 답변 지침은 원래 이 동작을 허용했고, README 6.1 문장만 맞췄다.
- 결정: 검색어 샘플링 랜덤성은 그대로 둔다(temperature 고정의 효과가 불확실하고 추론형 모델에서 거부될 수 있음). 검색어 지침(2~5단어, 다른 각도)도 유지.

### 6. 이전 답변 다시 쓰기

- 질문: "아까 삼성전자 답변 세 줄로 줄여줘"
- 1차:
  - Jev search 0.58 (answer 0.42) → 검색어 LLM은 검색이 필요 없다고 보고 빈 인자 `{}` → 검색 미실행 → Jev search 0.74 → "삼성전자 목표주가 전망" 검색 → answer. 18.9초.
  - 답변이 "제목·요약만 확인했고 본문은 확인하지 못했다"고 씀. 3번에서 같은 기사 본문을 이미 읽었는데도 그랬다. 원인은 답변 지침의 "이번 Turn에 도구 결과가 있으면 그 안의 내용만 근거로 쓴다".
- 검토한 대안: `recall` 도구(최근 Turn을 불러와 Jev에게 보여주기), search에 web/context 인자 추가. 답변 LLM은 원래 전체 대화를 받으므로 둘 다 answer와 같은 결과를 내는 중복 구조라서 채택하지 않았다.
- 수정 (`a8ff58b`): Jev answer 설명에 "답변 모델은 전체 대화를 본다"를 알리고, 답변 지침의 근거 범위를 "이번 Turn 도구 결과 또는 이전 대화"로 넓힘. 도구 결과가 없는 일반 질문에는 제한을 두지 않는 기존 조건은 유지.
- 수정 (`575528e`): answer 기준을 예시 나열 대신 규칙 하나로 정리. "대화에 이미 있는 것(이전 답변, 사실, 링크, Memory)이나 일반 지식으로 새 정보 없이 답할 수 있으면 answer".
- 2차: Jev answer, 5초 안팎. 3번에서 읽은 근거와 평균 목표주가를 살려 세 줄로 답함.

## 측정값

- Jev 응답: 0.2~0.5초.
- 검색어 작성 LLM: 2.4~9초. 한 번의 검색 흐름에서 가장 느린 단계다.
- 답변 LLM: 2~6.5초.
- Jev 입력: 이번 질문만일 때 520~620 토큰, 후보 5건 추가 시 약 1,800, 본문 1건(6,000자) 추가 시 약 +4,400. 한 Turn에서 긴 본문을 6~7건 읽으면 32k 한도에 닿는다. 이번 테스트에서 한 Turn에 읽은 본문은 최대 1건이었다.
- 답변 LLM 입력: 1~7번에서는 대화가 쌓이며 최대 약 19,000 토큰까지 커졌다. 이전 Turn의 도구 결과·본문을 그대로 저장했기 때문이다. 최종 답변만 저장하도록 바꾼 뒤 8~13번(Turn 9개)에서는 최대 약 5,000 토큰이었다.

## 남은 관찰 사항

1. 되묻기가 필요한 모호한 질문에서 Jev가 맥락 없이 search를 고르는 빈도 (5번).
2. 검색 뒤 두 번째 판단에서 answer와 search·read가 근소하게 갈리는 경우가 많다(2번 2차 0.58, 범용 문구 재확인 0.37 vs 0.33, 7번 0.54). 본문 없이 답하는 경우가 잦은지 실제 사용에서 본다.
3. 대화가 쌓일 때 답변 LLM 입력 증가: 최종 답변만 저장하도록 바꿔 크게 줄었다. 다음 Turn은 이전 답변에 적힌 내용만 알 수 있으므로, 답변에 빠진 세부사항이 필요한 요청이 잦은지 본다.
4. Jev 32k 한도: 한 Turn에 본문 2건을 읽었을 때 5,502 토큰이었다. 더 많이 읽는 경우는 아직 관찰하지 못했다.
5. 운영 로그: harness에는 Jev 선택·도구 실행 로그가 없다. PIA 연결 때 내용 없이 메타데이터(선택, 확률, 토큰, 시간)만 DEBUG로 남기는 것을 검토한다.
