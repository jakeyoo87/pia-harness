### A. 읽기 실패 후 같은 링크 반복 (14, 17-1, 18)

  - 인자 LLM은 후반에 "본문을 읽을 수 없다면…"이라는 goal을 쓰고, 마지막엔 인자 대신 "여러 차례 확인했지만 불러오지 못했다"는 문장을 냈다.

- 원인은 두 가지다.
  - 한 Turn에 같은 URL을 몇 번이든 다시 읽을 수 있다. web_fetch의 Turn당 1회 제한이 없어진 뒤 이를 막는 규칙이 없다.

## Codex 검토

`fe79374` 기록의 A~H와 `c11ca0a` 구현, `611aa04`의 60초 변경을 대조했다. 기록·코드 검토만 했고 실제 Jev·LLM·Exa·Jina 호출, 다른 파일 수정, 병합·AWS 변경·배포는 하지 않았다. B(일치한 발췌만 사용), D(링크 잡음 제거), F(현재 요청을 발췌 LLM에 전달)는 관측된 실패에 직접 대응한다. 다음은 수정 전에 정리할 실제 문제다.

### Blocker

1. **수정 7의 공급자 텍스트 앞 200자 기록은 비밀·내용 비기록 원칙과 충돌한다.** Exa 응답 앞부분은 검색어·후보 URL·본문 또는 오류 본문일 수 있다. 현재 측정 스크립트도 `TOOL_ARGS`, 후보 URL, 추출 URL·오류 문자열과 최종 답변을 출력한다(`tests/manual/smoke_flow.py:111-156, 271`). 합성 시나리오로만 쓰더라도 이 스크립트가 실제 사용자 입력으로 실행되면 값이 command output에 남는다. G는 본문 일부를 저장하는 대신 HTTP 상태, MCP `error/isError` 여부, content block 수·길이, 파싱된 후보 수처럼 **내용 없는 구조 정보**로 나누어 기록한다. 원문 재현이 필요하면 비밀값 없는 별도 합성 fixture를 만든다.
2. **수정 1은 A의 403 반복은 막지만, 빈 인자 `{}` 반복은 막지 못한다.** 현재 `generate_tool_call`은 JSON 객체 여부만 확인하고 도구 스키마의 필수 `urls`·`goal`은 검사하지 않는다(`openrouter.py:259-278`). `_web_extract`는 빈 인자를 정상 관측(`No goal`)으로 돌려주므로(`orchestrator.py:842-873`), 시도한 URL이 없어도 선택지가 남아 60초/20회까지 반복할 수 있다. 최소한 **필수 인자 없는 호출은 읽기 시도로 취급하지 않고 실패**시켜야 한다. 기존 `listed_urls`는 검색 후보를 결과 문구에서 한 번만 보여줄 뿐, URL 읽기 실행을 막는 상태는 아니다(`orchestrator.py:1371-1391`).

### Non-blocker

- URL당 1회 규칙은 Jina 403에는 잘 맞지만, 발췌가 goal별이라는 점에서 18번처럼 첫 goal을 고친 뒤 같은 페이지를 다시 읽는 것도 막는다. 수정 6을 넣고 18번을 다시 시험해 이 제한을 감수할 수 있는지 확인한다. 실제로 다른 goal 재발췌가 필요하면 그때 403처럼 확정적으로 읽을 수 없는 URL만 Turn에서 제외하는 방식으로 좁히면 된다. 지금 상태를 두 개로 나누어 미리 구현하지 않는다.
- **수정 8만으로 H의 원인은 드러나지 않는다.** Jev 어댑터가 HTTP 오류·timeout·JSON 오류를 모두 `jev.request_failed`로 바꾸므로(`jev.py:181-192`), 바깥 측정 도구의 예외 종류는 같다. 답변 호출 전체 52초만 재면 공급자 지연과 내부 재시도도 구분되지 않는다. production DEBUG 로그를 되살리지 말고 측정 경계에서 개별 HTTP 시도 시간, 안전한 HTTP status 또는 예외 class, 시도 횟수만 기록한다(본문·URL·query·예외 문자열 제외). 그러면 일시 실패와 지연을 재측정할 근거가 생긴다.
- **수정 3은 C의 확정 원인이 아니라 출력 잘림 가능성을 낮추는 값 조정이다.** 기록에서는 동일 페이지 재실행이 4개·395자로 성공했다. 현재 `openrouter.output_truncated`는 재시도 불가라(`openrouter.py:710`), 기존 최대 2회 재시도 경로에서 이 오류를 한 번 재시도하는 편이 근본 원인에 더 가깝다. 6개×1,000자 축소는 측정 후 필요할 때 정해도 된다.
- **수정 4는 발췌 LLM에 보내는 텍스트와 원문 대조에 쓰는 텍스트를 같은 결정적 정리 결과로 맞춘다.** Markdown 링크를 지운 뒤 모델이 돌려준 문장을 URL이 포함된 원문과 대조하면 정상 발췌도 불일치할 수 있다(`web_extract.py:46-63`). 페이지 상한 30,000자는 정리 뒤에 적용하고, 잘린 페이지의 `관련 내용 없음`은 기존처럼 `나머지는 확인하지 못함`이라고 표시한다.
- **수정 5의 시각은 저장용 사용자 메시지가 아닌 이번 Prompt의 `CURRENT_USER` 앞에만 붙인다.** `batch[-1].accepted_at`을 `YYYY-MM-DD HH:MM +09:00`처럼 연도·시간대가 분명하게 변환하면 Jev·인자·답변 LLM이 모두 보고, DB Turn 원문과 다음 Turn의 `PREVIOUS_USER`는 바뀌지 않는다(`orchestrator.py:1014-1025, 1124-1139`). 시스템 지침 앞부분을 바꾸지 않는 캐시 판단도 맞다.
- **수정 6은 같은 OpenRouter 공급자에 이미 전달되는 이번 요청만 추가하므로 새 처리자나 Memory 노출은 아니다.** goal의 종목 추측이 원문 요청과 충돌할 때 발췌 LLM이 페이지와 사용자의 실제 질문을 우선하도록 지침을 적고, 18번에서 재확인한다. 실제 사용자 입력을 측정 로그에 남기지 않는 것은 별개로 지킨다.
- **A안/B안 해석은 아직 가설이다.** 403 반복은 실패 URL도 계속 선택지에 남는 경계, 빈 `{}`는 필수 인자 미검증, 잘못된 goal은 페이지를 보기 전의 추측에서 생겼다. 답변 모델 하나가 도구를 골라도 이 세 문제가 자동으로 사라지지는 않는다. 19번의 조기 종료도 첫 Exa 후보에 목표 ETF가 있었는지 확인한 뒤 Jev 판단과 검색 recall을 구분해야 한다. 수정 후 같은 시나리오를 다시 측정해 B 여부를 결정하는 순서는 맞다.

## Codex 구현 검토

`main c225b8b...7232b67`의 최종 diff와 1~3차 측정 기록을 대조했다. 실제 모델·Exa·Jina·Broker 호출, 다른 파일 수정, 병합·AWS 변경·배포는 하지 않았다. 오프라인 unittest 166개는 통과했다. 지난 검토의 빈 인자 반복은 읽기 실행 전 검사와 부분 답변 경로로, 원문 앞 200자 기록은 크기만 남기는 방식으로 해결됐다. 발췌는 정리된 원문과 대조해 틀린 근거만 버리며, 사용자 요청·KST 시각은 Prompt에서만 쓰고 저장 Turn 원문은 바꾸지 않는다. `confirm`의 실행 확정 경로도 변경되지 않았다.

### Blocker

1. **검증된 근거가 없어도 요약의 사실 주장이 남는다.** `JinaPageExtractor.extract`는 원문에 없는 quote를 걸러도 `summary`는 URL만 제거해 반환한다(`web_extract.py:52-86`). quote가 모두 탈락하면 `read; 0 quote(s) checked`와 숫자·날짜가 든 요약이 함께 Jev와 답변 LLM에 전달된다(`orchestrator.py:903-935`). 요약은 원문 대조 대상이 아니므로 "요약 + 검증된 근거"에서 요약 자체가 검증됐다고 볼 수 없다. 최소 수정은 **검증된 quote가 하나도 없을 때 요약을 증거로 싣지 않고** 미확인 상태로 돌리는 것이다. 유효 quote가 있어도 수치·기준일은 그 quote에만 근거해야 한다. 3차 측정 21번에서 자료 적용일을 확인하지 못했는데 첫 줄은 `9월 28일 기준`이라고 한 모순이 실제로 남았다. 이번 요청 앞의 `[Received ... KST]`가 자료 기준일이 아니라는 점을 명시하고, 출처에 기준일이 없는 회귀 사례에서 당일 기준이라고 말하지 않는지 확인한다. 날짜 혼동의 정확한 원인은 로그만으로 확정할 수 없으나, 모순 자체는 재현된 답변 결함이다.

### Non-blocker

- **URL 경계의 핵심은 유지됐다.** 거부·중복 URL은 결과에 다시 적지 않고, 요약의 http(s) URL을 지우며, 근거는 링크를 제거한 원문에서 확인한다. 따라서 모델이 새로 지어낸 URL을 그대로 다음 읽기 허용 목록에 넣는 경로는 확인되지 않았다. 다만 Markdown 링크는 제거돼도 페이지의 **맨 URL**은 원문·검증 quote에 남을 수 있고, `_conversation_urls`는 모든 `TOOL_RESULT`에서 URL을 수집한다(`orchestrator.py:1427-1436`). README의 "이번 Turn 검색 후보만"이라는 설명과 다르다. 페이지에 실제로 있던 링크도 따라갈 정책이면 설명을 맞추고, 검색 후보만 허용하려는 정책이면 이 범위를 좁힌다. 새 필터 계층을 미리 늘릴 필요는 없다.
- **빈 인자·같은 링크 반복·한도는 안전하게 끝난다.** 필수 필드가 빈 읽기 호출과 새 URL이 없는 추출 호출은 도구 실행 전에 `limit_reached`로 끝나며, `read_urls`는 Turn 안에서만 유지된다(`orchestrator.py:522-579, 835-935`). 14번이 12초로 끝난 측정과 맞는다. 이 방식은 다른 goal로 같은 URL을 다시 추출하지 못한다는 기존 제한을 남기지만, 18번이 첫 시도에 성공했으므로 지금은 추가 상태 없이 수용 가능하다. 주문 `confirm`에는 읽기 횟수 상한을 적용하지 않는다.
- **H의 측정은 부분 개선이다.** HTTP 응답을 받은 경우 시도별 시간·상태가 남고 출력 잘림은 발췌 호출에서만 한 번 재시도한다. 하지만 응답 전 전송 오류에는 response hook이 없고 Jev 어댑터는 이를 모두 `jev.request_failed`로 감싼다(`jev.py:181-192`); 1차 측정 2번 유형의 원인은 여전히 `JevDecisionError`만으로 구분되지 않는다. 재발할 때에만 안전한 전송 오류 class를 어댑터 경계에서 보존하면 충분하다. 현재 수동 smoke는 합성 시나리오의 인자·URL·답변을 그대로 출력하므로 실제 사용자 입력으로 실행하지 않는다(`tests/manual/smoke_flow.py:111-185, 270-320`).
- **19번 결과는 A안의 현재 품질 한계다.** 검색 1회와 기사 3개 읽기 뒤 출처를 달아 답했지만 목표 ETF는 못 찾았다. 사용자 결정대로 A안을 유지하되, Hermes와 동등한 조사 깊이를 달성했다고 기록하지 않은 현재 판정이 정확하다. 한도·상태·후처리 추상화를 더 늘리기보다 이 시나리오를 이후 비교 기준으로 유지한다.
