# 본문 읽기를 web_fetch 도구로 바꾸는 계획

## 문제

실제 Bot 대화(2026-09-27)에서 "주요 이슈는?" → 검색 요약 답변 → "기사들 본문 읽어보고 요약해달라"에 본문을 읽지 못하고 "링크를 열 수 없다"고 답했다.

- 지금 본문 읽기 선택지(`read:c1`, `read:u1`)는 **이번 Turn의 검색 후보**와 **이번 메시지의 URL**에만 생긴다.
- Turn에는 요청과 최종 답변만 저장되므로, 다음 Turn에는 직전 답변에 링크가 있어도 읽을 선택지가 없다.
- 답변 LLM은 링크를 직접 열지 못한다(웹 기능 없는 `openai/gpt-6-luna`에 링크를 주고 요약을 요청하면 "본문을 확인할 수 없다"고 답함, 2026-09-27 확인).

## 실패 사례 상세

실제 Bot(harness 0.4.0, main `b1d3ef6` 코드)에서 사용자가 보낸 세 메시지:

| Turn | 사용자 메시지 | Jev 선택 | 결과 |
|---|---|---|---|
| 1 | 전력기기 회사 관련 주요 이슈는 ? | search → answer | 후보 5건의 제목·요약으로 답함. "본문은 확인하지 못했다"고 밝힘. 답변에 기사 링크 5개(Markdown) |
| 2 | 주요 기사들 위주로 요약부탁 | answer | 요약만 다시 정리. 본문 없음 |
| 3 | 기사들 본문 읽어보고 요약해달라는 말인데 | answer | "현재 이 대화에서는 링크를 열어 기사 본문을 직접 읽을 수 없습니다" (사실과 다름) |

원인 분석:

- Turn 1: `read:c1…c5` 선택지가 있었지만 Jev가 제목·요약으로 충분하다고 보고 answer를 골랐다. 시나리오 테스트에서도 search 뒤 answer가 흔하다. 설계상 허용된 동작이다.
- Turn 2·3: 검색 후보는 Turn에 저장되지 않아 `read:c…`가 없었고, 사용자 메시지에 URL이 없어 `read:u…`도 없었다. 기사 링크는 직전 답변(Jev의 `PREVIOUS_ANSWER`)에 있었지만 읽기 대상이 아니었다. Jev 선택지는 answer·search·order뿐이었다. **본문을 읽을 수단이 없는 상태**였다.
- search를 다시 골랐다면 같은 기사가 후보로 나와 읽을 수 있었지만, Jev는 "이미 답한 기사를 다시 찾기"로 판단하지 않았다.
- 답변 LLM은 링크를 직접 열지 못한다. 웹 기능 없는 `openai/gpt-6-luna`에 "이 기사 본문을 읽고 요약해줘: <URL>"을 보내면 입력 39 토큰으로 "링크의 기사 본문을 직접 확인할 수 없어요"라고 답했다(2026-09-27).

근본 원인: 읽기 선택지가 **같은 Turn 안에서만 존재하는 숨은 상태**(검색 후보)에 묶여 있어서, 사용자에게는 보이는 링크를 AI가 읽을 수 없는 경우가 생긴다.

## 검토한 대안

| 대안 | 판단 |
|---|---|
| A. 직전 답변의 링크도 `read:u…` 선택지로 추가 | 이번 사례는 해결되지만, 더 이전 답변의 링크나 "두 번째 기사만" 같은 요청은 여전히 못 읽음. 선택지 이름으로 대상을 고르는 구조의 한계가 남음 |
| B. 답변 LLM에 OpenRouter 웹 플러그인을 켬 | harness는 OpenRouter 내장 Web Search를 쓰지 않기로 함(README 6.1). 무엇을 읽었는지, 사설 주소 차단·유료 기사 판단을 harness가 통제할 수 없음 |
| C. Jev 기준을 바꿔 search 뒤 본문을 더 자주 읽게 함 | Turn 2·3 문제는 그대로(읽을 선택지 자체가 없음). 답이 느려지고 비용 증가 |
| D. **URL을 인자로 받는 일반 도구 `web_fetch`** (채택) | 대화에 보이는 링크면 언제든 읽음. 여러 개를 한 번에, 필요한 것만. 읽기 특별 처리 코드가 줄어듦. 대가: 읽을 때 인자 작성 LLM 호출 1회 |
| D에서 선택지를 항상 표시 | 읽을 게 없어도 고를 수 있어 반복 위험(주문 도구에서 Jev가 같은 도구를 120초 동안 반복한 사례, `tests/manual/records/2026-09-27_execution.md`). 그래서 표시 조건을 둠(최종: 한 Turn에 한 번, 아래 검토 반영) |

## 결정 (사용자 합의)

- `read:후보ID` 선택지를 없애고, URL 목록을 인자로 받는 일반 읽기 도구 **`web_fetch`** 하나로 바꾼다.
- 읽을 수 있는 URL = **대화에 나온 URL**: 이번 메시지, 이번 Turn 도구 결과(검색 후보), 이전 대화의 요청·답변·요약. Markdown 링크 `[제목](URL)`도 포함. **장기 Memory 안의 URL은 제외**한다.
- 인자는 LLM이 쓴다: `{ "urls": [1~5개] }`. 요청에 필요한 링크만 고르고, 대화에 나온 URL을 그대로 복사한다.
- 대화에 링크가 있고 이번 Turn에 아직 쓰지 않았을 때만 `web_fetch` 선택지를 보여 준다(한 Turn에 한 번, 아래 검토 반영).
- 여러 URL은 동시에 가져와 URL별 결과를 하나의 도구 결과로 합친다.

## 동작

```text
◇ 대화에 링크가 있고 이번 Turn에 web_fetch를 안 썼나? 아니면 선택지 없음
    ↓ 있음
◇ Jev가 web_fetch 선택
    ↓
LLM이 인자 작성 { urls: [...] }
    ↓
URL마다 (동시에)
  ├─ 대화에 없는 URL        → 읽지 않음, "대화에 없는 링크"
  ├─ 이번 Turn에 이미 읽은 URL → 읽지 않음, "이미 읽음"
  └─ 그 밖                 → 본문 1건 (성공: 기사당 약 6,000자 / 실패: 읽지 못함)
    ↓
URL별 결과를 합쳐 이번 Turn Context에 추가 → Jev 다시 선택
```

## 구현 (pia-harness)

- `orchestrator.py`
  - `read:` 선택지, 후보 ID(`c1`, `u1`), `_Link`, `_message_links`, `_tool_result_text`의 후보 번호 매기기를 없앤다.
  - 기존 `read_url` 인자를 그대로 쓰는 내장 읽기 도구 `web_fetch`를 둔다(PIA 조립 코드는 바뀌지 않음). 인자 작성은 다른 도구와 같이 `build_tool_call`로 한다.
  - 읽을 수 있는 URL은 조립된 Context의 `USER_TURN`·`ASSISTANT_TURN`·`CURRENT_USER`·`TOOL_RESULT`에서 모은다(Summary·Memory 제외).
  - 표시 조건: 읽을 수 있는 URL이 있고 이번 Turn에 아직 쓰지 않았을 때.
  - 도구 이름 예약: `web_fetch`는 등록 도구 이름으로 쓸 수 없다.
- 검색 결과 텍스트는 후보 ID 없이 날짜·제목·요약·링크만 둔다.
- 본문 추출(readability-lxml), URL 안전 검사(http·https, 사설·loopback·metadata 거부, redirect마다 재검사, 시간·크기 상한), 네이버 뉴스 링크 우선은 지금과 같다.
- Jev 입력 크기: 도구 결과가 커지면 Jev 입력 한도(약 32k 토큰)를 넘을 수 있다. Jev에 보내는 `TOOL_RESULT`만 결과당 앞 1,000자로 자른다. 답변 LLM은 전체를 받는다.
- README 1번(읽기 도구 흐름, `next_action` 값), 6.1(공통), 6.1.1(후보 ID 삭제), 6.1.2(새로 씀). 선택지 표시 조건 원칙 한 줄: "선택지는 대화에 보이는 것이나 명시한 안전 규칙에만 묶는다."
- 버전 `0.4.1`.

## 테스트

- 단위: 직전 답변의 Markdown 링크를 읽음, 대화에 없는 URL 거부, 한 번 쓰면 이번 Turn에 선택지 없음, 링크가 없으면 선택지 없음, 여러 URL 동시 읽기와 결과 합치기, 1~5개 제한, Memory 안 URL 제외, Jev용 web_fetch 결과 자르기(검색 결과는 자르지 않음)
- 수동 시나리오(`--set read`, 실제 Jev·LLM·NAVER, 비용 발생 → 사용자 승인): 기존 19개 전체 + 새 시나리오 "전력기기 회사 관련 주요 이슈는?" → "기사들 본문 읽어보고 요약해줘"(web_fetch 기대), "두 번째 기사만 자세히"(1개만 읽기 기대)

## Codex 계획 검토 반영 (2026-09-27, `fd7df8b` 대상)

- Jev 지침의 "예전 링크를 가리키면 answer"가 실패를 다시 만들 수 있다: 본문을 읽어 달라는 요청이고 `web_fetch`가 있으면 예외로 `web_fetch`를 고르도록 한 문장을 더했다.
- 실패한 URL·대화에 없는 URL 반복: URL별 상태를 추적하는 대신 **`web_fetch`는 한 Turn에 한 번만** 쓰게 했다(사용자 확인, 상태와 규칙이 가장 적은 안). "안 읽은 URL" 추적은 없앴다.
- 도구 결과 맨 앞에 URL별 상태 줄을 둬, Jev용 1,000자 자르기 뒤에도 모든 결과가 보인다.
- Summary는 모델이 쓴 글이라 URL 출처에서 뺐다. 요약된 옛 링크는 읽을 수 없다고 README에 적었다.
- `read_url`을 넘기면 인자 작성 함수가 필수라는 생성자 검증을 더했다. `web_fetch`는 등록 도구 이름으로 쓸 수 없다.

## Codex 구현 검토 반영 (2026-09-27, `c67eab0` 대상)

- Blocker: 1,000자 자르기가 검색 결과에도 적용돼 뒤쪽 후보가 Jev에게 안 보일 수 있었다. 자르기는 `web_fetch` 결과에만 적용한다(앞의 도구 요청이 `web_fetch`인 결과). 긴 검색 결과의 후보 5건이 모두 보이는 테스트를 더했다.
- 링크 없는 답변을 거친 세 번째 Turn에서 읽는 테스트, 6개 요청 시 5개만 읽는 테스트를 더했다.
- 계획 본문의 옛 설명(Summary 포함, "안 읽은 URL")을 최종 결정에 맞게 고쳤다.
- 작은 수정이라 재검토 없이 Claude가 확인하고 verify-harness로 검증한다.
