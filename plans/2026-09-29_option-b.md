# B안: 모델 하나가 도구를 고르고 답한다 (Hermes식)

브랜치 `claude/option-b` (기준 main `50acd3f`, 0.6.0 미릴리스). 사용자와 대화로 방향을 정했다. A안 기준 계획 `plans/2026-09-29_tool-categories.md`(브랜치 `claude/tool-categories`)는 보류했고, 거기서 정한 것 중 B안에도 맞는 것은 이 계획으로 가져왔다. 0.6.0 릴리스와 PIA 연동은 이 작업 뒤에 한 번에 한다.

## 배경

- 지금(A안)은 Jev가 선택지 중 하나를 고르고(확률만, 글 없음), 인자는 별도 LLM(luna)이, 답변은 또 다른 호출(luna)이 쓴다.
- 판단이 Jev와 인자 LLM으로 나뉘어 생긴 문제와, 그것을 막으려는 코드 규칙이 쌓였다.
  - 21번(4차): Jev가 검색 발췌만 보고 answer(0.69)를 골라 비중을 답했다. 어떤 링크에 표가 있는지 보는 모델은 이 결정에 관여하지 못한다.
  - 19번: 조사 깊이가 얕다(471760 미발견).
  - 보완 규칙: web_extract 표시 조건, 빈 인자·새 링크 없음이면 조사 종료, 실행 준비 뒤 Jev 생략, 직전 Turn 4,000자, Jev 요청 64KB.
- 사용자는 하드코딩이 늘어나는 것을 경계하고, 목표는 Hermes 수준의 깊은 조사다.
- 비용은 결정 변수가 아니다. Jev 입력 $0.042/M(21번 기준 Turn당 약 $0.0003), luna 입력 $0.10/M(캐시 $0.01/M), 출력 $0.50/M. A안도 매 단계 인자 LLM이 대화 전체를 읽으므로, B안은 Jev 호출이 빠지는 만큼 같거나 싸다.
- Jev를 고른 원래 이유는 "Jev + Nemotron 무료" 조합이었다. 무료 등급은 서비스용으로 부적합하다고 판단했다(시험 3회 중 1회 과부하, 4.5~17초, 이용 한도, 데이터 정책).
- `openai/gpt-6-luna`는 OpenRouter에서 `tools`·`tool_choice`를 지원한다.

## 설계

### 1. 루프 (Hermes 참고)

```text
사용자 요청
    ↓
Context 구성 (System·Memory·Summary·이전 Turns·이번 요청 + 이번 Turn의 도구 호출·결과)
    ↓
◇ luna 호출 (tools = 등록된 도구 전체, tool_choice=auto)
  ├─ 도구 호출(들) → Harness가 실행 → 결과를 Context에 추가 → 다시 luna
  └─ 도구 호출 없이 글 → 그 글이 답변 → 출처 정리 → Memory 처리 → 전달·Turn 저장 → 종료
```

- 답변은 따로 부르지 않는다. 도구 호출 없는 응답의 본문이 최종 답변이다. `answer` 선택지·답변 전용 호출·`{"answer": ...}` 포장은 없어진다.
- 한 응답의 도구 호출은 **실행 전에 묶음 전체를 검사**한다(Codex B2).
  - 실행 도구 호출은 한 묶음에 5개까지 준비한다(주문 여러 건을 한 번에 요청하는 경우). 넘는 호출 ID에는 "한 번에 5건까지" 결과를 붙인다. 준비는 순서대로 하고 각각 확인 대기가 된다.
  - `confirm` 호출이 있는 묶음에서는 `confirm`만 실행하고, 다른 호출 ID에는 "확정 뒤 다시 요청" 결과를 붙인다(→ 5).
  - 읽기 호출은 남은 한도(20회)까지만 실행하고, 넘는 호출 ID에는 "조사 한도에 닿아 실행하지 않음" 결과를 붙인 뒤 최종 답변으로 간다(→ 2).
  - 같은 묶음에서 여러 읽기 호출이 같은 URL을 요청하면 실행 전에 이번 Turn의 읽은 URL로 예약해 한 번만 읽는다.
  - 읽기는 동시에 실행하고, 결과는 **원래 호출 순서대로 모든 호출 ID에 정확히 하나씩** 붙인다. 실행 도구가 있으면 읽기와 함께 처리하고 다음 호출은 도구를 끈다(→ 3).
- 도구 인자 오류(JSON 아님, 필수 칸 없음, 스키마 불일치)는 도구를 부르지 않고 오류 문장을 그 호출의 결과로 돌려준다. 모델이 고쳐 다시 부른다(Hermes와 같음).
- 모델 호출 자체의 실패(HTTP·전송·형식)는 지금처럼 재시도 후 Turn 실패로 알린다.

### 2. 한도와 부분 답변

- 한도는 지금과 같다: 읽기 도구 호출 20회, 읽기 루프 60초.
- **입력 크기는 실제로 보낼 요청 전체로 센다**(Codex B3): messages, 이번 Turn의 `tool_calls`/`tool` 메시지, 등록된 도구 스키마. `count_input_tokens`를 루프 요청 payload 기준으로 바꾼다. 80% Compaction 판단도 이 값으로 한다.
- 다음 루프 호출이 예산에 들지 않으면 한도와 같이 최종 답변으로 간다.
- 한도에 닿으면 도구 없이(`tools`를 빼서 요청도 줄임) `RESEARCH_LIMIT_NOTICE`를 붙여 한 번 더 부른다. 그 답변으로 끝낸다(지금의 부분 답변 경로, Hermes finalizer와 같음). 이 최종 호출도 같은 예산으로 확인한다.
- 도구 결과는 도구마다 상한이 있어(검색 후보 5건·요약 400자, 본문 추출 페이지당 약 2,000자·최대 5개) 20회를 다 써도 luna Context(1,050,000 토큰)의 작은 부분이다. 그래도 Compaction 뒤에 최종 호출이 들지 않으면 지금처럼 `CONTEXT_OVERFLOW`로 Turn을 끝낸다(도구 결과를 잘라 억지로 답하지 않음).
- 없어지는 A안 보완 규칙: 선택지 표시 조건, 빈 인자·새 링크 없음이면 조사 종료, Jev 요청 64KB, Jev용 직전 Turn 4,000자. 반복은 모델이 결과를 보고 판단하고, 한도가 상한을 막는다.

### 3. 도구 대분류와 양식

- 대분류는 읽기·실행 둘이다(답변은 도구가 아님, 코딩은 README에만 "미구현"). 실행 뒤 동작·한도·실패 규칙은 대분류가 정한다.
  - 읽기(`ReadToolDefinition`): 결과를 넣고 계속. 20회·60초 한도. 예상 가능한 실패는 결과 문장, 코드 오류는 `TOOL_FAILED`.
  - 실행(`ExecutionToolDefinition`): 준비만 하고 확인 대기를 만든다(→ 5). 준비 뒤 다음 호출은 도구를 끄고 답변을 받는다(같은 도구 반복을 막는 지금 규칙을 도구 끄기로 대신).
- 도구 하나는 이름, 설명(모델용, 언제·어떻게 쓰는지), 인자 스키마, 실행을 갖는다. A안 계획의 `description`/`guide` 분리는 필요 없다(모델 하나가 모두 읽음).
- 도구의 프롬프트는 그 도구 파일에 둔다. `web_extract`의 설명·발췌 지침은 `web_extract.py`로 옮기고, 모델 어댑터는 호출만 한다.
- 뒤 정리 LLM은 필요한 도구만 자기 안에서 부른다(지금은 `web_extract`의 요약·근거).
- 이름을 맞춘다: `BrokerOrderTool.definition()` → `.tool()`, `JinaPageExtractor(...).tool()`, `ExaWebSearch().tool()`.

### 4. web_extract와 URL 경계

- `web_extract`는 일반 읽기 도구가 된다. `extract_page` 생성자 인자와 orchestrator 안의 전용 경로(`_web_extract`)를 없앤다.
- URL 경계는 읽기 대분류 규칙으로 둔다. `ReadToolDefinition.url_argument`(예: `"urls"`)를 선언한 도구에 대해 Harness가 대화(사용자 메시지·저장된 답변·이번 Turn 도구 결과)에 없는 URL과 이번 Turn에 이미 읽은 URL을 걸러 부른다. 걸러낸 개수만 결과에 적고 URL은 다시 적지 않는다. 읽을 것이 없으면 도구를 부르지 않고 "새로 읽을 링크가 없음"을 결과로 돌려준다.
- 페이지별 처리(`PageReadError` → "읽지 못함", 요약·근거 대조)는 도구 안에 그대로 둔다.

### 5. 주문 확인은 `confirm` 도구로 (사용자 결정: 최대한 도구로, Hermes 방식)

버튼은 쓰지 않는다. 확인도 모델이 도구로 처리하고, 코드 규칙 하나로 조작 경로를 막는다.

- 실행 도구(`order`)를 부르면 준비만 하고 확인 대기를 만든다. 여러 건이면 건마다 대기가 생긴다(사용자당 최대 5건). 도구가 만든 확인 문장을 답변 끝에 붙이고, 대기는 지금처럼 **전달이 성공한 뒤에만** 저장한다.
- 다음 Turn에 대기가 있고 5분 이내면, Harness가 Context에 "확인 대기: ID — 요약" 목록을 넣고 `confirm` 도구(인자 `{action_ids: [...]}`)를 켠다. 대기가 없으면 `confirm`은 도구 목록에 없다.
- 모델이 사용자 메시지("응", "삼성만 해줘")를 보고 확정할 대기를 골라 `confirm`을 부른다. Harness는 고른 대기를 **다시 쓰지 않고 그대로** 실행한다(같은 `request_id`로 중복 주문 방지). 실행 확정(→ README 2) 뒤 새 메시지는 기다리고, 결과로 도구 없이 답한다.
- **규칙 하나: `confirm`은 그 Turn의 첫 모델 응답에서만 실행한다.** 이미 도구 결과(검색·본문 등 외부 자료)가 Context에 들어온 뒤의 `confirm`은 실행하지 않고 "확정은 다른 도구보다 먼저 해야 한다"를 결과로 돌려준다. 외부 자료를 읽기 전이라 모델이 판단하는 근거는 사용자 메시지뿐이며, 페이지 속 문장에 속아 확정하는 경로가 막힌다.
- 조건 변경("28만원에")은 모델이 `order`를 다시 불러 새 대기가 된다. 취소("취소해", 다른 이야기)는 도구 없이 답하면 된다. 대기는 **다음 Turn이 끝나면 모두 버린다**(쓰였든 아니든, 새로 만든 것만 남음, 지금 규칙). 처리 중 새 메시지로 생성이 다시 시작되면 합쳐진 메시지 기준으로 같은 대기를 다시 본다(지금의 `offered` 스냅샷 방식).
- 별도 입구(`confirm_pending`/`cancel_pending`)와 `pending_action_id`, 버튼 인계는 없다. 따라서 Codex B1의 버튼·새 메시지 경쟁도 생기지 않는다.

### 6. Memory: `memory` 도구 (사용자 결정, Hermes 방식)

Jev가 answer와 함께 정하던 `MemoryAction`(NONE/UPDATE/FORGET)의 주체가 사라진다.

- **`memory` 도구**. 인자 `{action: "update" | "forget"}`. 모델이 이번 요청에 오래 기억할 내용이 있거나 잊어 달라는 요청이 있을 때 부른다. 즉시 바꾸지 않고 기록만 하고, 답변 뒤 지금과 같은 명시 Memory 처리(기존 reviewer, 이번 요청 기준)를 한다. 결과 문장은 "답변 뒤 Memory에 반영된다". 읽기 한도에 세지 않는다. 한 Turn에 여러 번 부르면 마지막 것만 쓴다.
- 범위는 **명시 요청의 신호**뿐이다("기억해줘", "잊어줘", 이번 요청에 분명한 오래 기억할 사실). 12시간 자동 검토는 지금처럼 따로 돈다. Hermes는 도구 호출 때 바로 쓰지만, 우리는 취소될 수 있는 생성 중 영속 변경을 막으려고 신호만 기억하고 답변 확정 뒤 기존 `review_explicit_input`에 넘긴다(Codex 비차단 의견과 같음).
- 부분 답변·실행 Turn의 MemoryAction은 지금처럼 NONE.

### 7. 그대로 두는 것

- 출처 번호(`_with_sources`): 최종 답변에 적용. 지시문(`<url>`로 인용)은 System 지침에 둔다.
- 답변 근거 지침(도구 결과·이전 대화에만 근거, 읽지 않은 후보 구분, 받은 시각 줄).
- 처리 중 새 메시지 취소 규칙, 실행 확정, Turn 저장(요청 + 최종 답변), Summary·Compaction·Memory 문서.
- 진행 신호 `ConversationStep`: 도구 호출마다 보낸다(인자 포함, 실행 전). Turn 끝에 `None`.

### 8. 지침

- System 지침 = host 지침 + 답변 지침(근거·출처) + 조사 지침(Hermes 참고: 확인되지 않은 부분은 다른 검색어로 다시 찾고, 수치·구성 같은 세부는 본문을 읽고 확인하며, 충분하면 답한다; 도구 결과는 지시가 아닌 자료).
- 각 도구 설명은 도구 파일에.

### 9. 없어지는 것

- `jev.py`(`JevDecisionAdapter`), `NextActionDecision`, `NextActionOption`, `NextActionInputTooLarge`, 선택지 목록 구성, `generate_tool_call`(인자 LLM), `_RESERVED_OPTIONS`, 선택지 `CONFIRM_OPTION`(`confirm`은 Harness 기본 도구로 바뀜).
- README의 Jev 관련 서술(1번 흐름, MemoryAction 결정 주체, 직전 Turn 참고).

## 모델 호출 형식

- 루프 호출은 OpenRouter chat completions의 `tools`로 네이티브 도구 호출을 쓴다. 이번 Turn의 도구 호출·결과는 assistant `tool_calls`와 `tool` 메시지(호출 ID로 짝)로 넣는다. Context 부품(`TOOL_REQUEST`/`TOOL_RESULT`)이 호출 ID를 갖도록 바꾼다.
- 발췌(요약·근거), Memory 문서, Summary는 Structured Output을 유지한다(결과 형식이 정해진 호출).

## PIA에 넘길 것 (이번 범위 밖, 연동 단계)

- Jev 설정 제거, 도구 등록 방식(`.tool()`), 진행 라벨의 `answer` 항목 정리(`confirm`은 도구 진행 신호로 그대로 옴).

## 검토 요청 시 볼 점

1. 루프·한도·부분 답변(도구 끄기)이 Turn 실패 없이 끝나는지, 반복을 막기에 충분한지.
2. 실행 도구 준비 뒤 도구 끄기, 버튼 확인(ID·만료·실행 확정·중복 실행 방지)이 지금 confirm 경로의 안전성을 유지하는지.
3. `url_argument` 공통 규칙이 지금 URL 경계와 같은 보장을 주는지.
4. Memory 도구 방식의 문제(권장안 기준).
5. 네이티브 도구 호출로 바뀌는 Context 구성(호출 ID, 여러 호출, 캐시)에서 놓친 것.
6. 빼도 되는 것, 빠진 것.

## Codex 검토

기준 `main 50acd3f`의 orchestrator·Context·OpenRouter adapter·주문 도구와 이 계획을 대조했다. 계획 검토만 했으며 코드 변경, 병합, AWS 변경, 배포, 실제 모델·공급자 호출은 하지 않았다. B안의 단일 모델 루프와 도구 분류는 A안의 판단/인자 분리를 줄이는 방향으로 적절하다. 다만 아래 경계는 구현 전에 계획에 고정해야 한다.

### 차단

1. **버튼 확인과 새 메시지의 경쟁 조건 (§5, 61–64행).** 현재 `submit`은 새 메시지를 받아도 `_pending_actions`를 즉시 지우지 않고, 일반 Turn의 전달이 끝난 뒤에야 지운다(`orchestrator.py` 435–447, 1276–1280행). B안에서 사용자가 확인 문장을 받은 뒤 “아니, 28만원으로 바꿔”를 보내고 그 처리 중 옛 [확인]을 누르면, 별도 `confirm_pending` 입구가 옛 주문을 실행할 수 있다. 새 메시지를 수락하는 순간 옛 대기를 무효화하고, 확인·취소는 동일한 사용자 `state_lock` 안에서 ID·만료를 검사하며 대기를 한 번만 선점해야 한다. 확인 선점과 `_claim_commit`은 하나의 원자적 상태 전환이어야 하며, 이후 실행·전달은 기존처럼 shield된 COMMITTING 경로를 사용해야 한다. PIA 연동 시에는 버튼을 누른 Telegram 사용자뿐 아니라 그 시점의 회원 실행 자격도 확인해야 한다. 현재 PIA의 callback 분기는 일반 메시지의 `GENERAL_AI` gate보다 앞에 있다(`app/application.py` 115–126, 175행).

2. **한 응답의 복수 도구 호출을 배치 단위로 검사해야 한다 (§1–2, 32·38행).** “읽기는 동시에, 실행은 하나만”은 모델이 주문 도구를 두 번 호출한 응답을 어떻게 처리하는지 정하지 않는다. 하나씩 준비하면 마지막 대기만 남거나 서로 다른 확인 문장이 한 답변에 섞일 수 있다. 또 한 응답이 읽기 도구 20개를 넘게 내면 호출별 검사만으로 Turn 한도를 초과한다. 실행 전에 배치 전체를 검사해 실행 도구가 둘 이상이면 아무것도 준비하지 않고 각 호출 ID에 오류 `tool` 결과를 붙인다. 읽기 호출은 남은 20회 범위까지만 실행하고 나머지 ID에는 한도 결과를 붙여 최종 답변으로 보낸다. 실행 도구가 하나이고 읽기 도구도 있으면 모든 호출 ID에 정확히 한 결과를 붙인 뒤 다음 모델 호출로 넘기면 된다. 완료 순서가 달라도 원래 호출 순서로 결과를 배치하면 충분하다.

3. **기존 Context 예산을 그대로 쓰면 네이티브 요청의 크기를 잘못 셀 수 있다 (§2·모델 호출 형식, 38–39·93행).** 현재 `OpenRouterAdapter.count_input_tokens`는 구조화 답변 payload의 `messages`와 `response_format`만 센다(`openrouter.py` 238–239, 468–479행). B안 요청에는 등록된 모든 `tools` schema와 assistant `tool_calls`/`tool` 응답이 추가된다. 실제 전송 payload를 기준으로 예산을 다시 세지 않으면 80% compaction 시점을 놓치거나 모델 한도 오류가 난다. 또 `_assemble_with_overflow`는 도구 관측이 한도를 넘으면 compaction 후에도 `CONTEXT_OVERFLOW`로 끝날 수 있다(`orchestrator.py` 1019–1033, 1076–1089행). “한도면 도구를 끄고 반드시 답한다”는 보장은 입력이 최종 답변 호출에 들어갈 때에만 성립한다. 구현은 최종 호출도 같은 예산으로 확인하고, 관측 자체가 너무 커서 들어가지 않는 경우의 결과를 명시해야 한다.

### 비차단·사용자 결정

- **Memory (§6).** 권장 `memory` 도구는 즉시 쓰지 않고 최종 답변 확정 시 기존 `review_explicit_input`에 연결하는 방식이면 취소된 generation의 부작용을 만들지 않는다. 다만 자동 검토는 지금도 별도로 돌아가므로, 명시 Memory 요청용 신호만 이 도구에 맡긴다는 범위를 정하면 충분하다. §6이 “사용자 확정 필요”인 만큼 구현 전 권장안과 12시간 자동 검토만 쓰는 대안 중 하나를 확정해야 한다. 추가 Memory 상태기계는 필요 없다.
- **URL 경계 (§4).** 공통 `url_argument`는 현재 `_conversation_urls`의 입력 종류(`USER_TURN`, `ASSISTANT_TURN`, `CURRENT_USER`, `TOOL_RESULT`; Summary·Memory·`TOOL_REQUEST` 제외)를 그대로 쓰면 기존 보장을 유지한다(`orchestrator.py` 274–284, 1469–1478행). 거부 URL을 결과에 되쓰지 않는 규칙도 유지한다. 같은 모델 응답의 병렬 읽기 두 개가 동일 URL을 요청하면 실행 전에 한 배치의 `read_urls`에 예약해 중복 읽기를 막으면 된다. URL 읽기 최대 5개는 도구 schema/도구 내부에 그대로 두고 공통 규칙에 중복시키지 않아도 된다.
- **PIA 버튼 인계 (§5·PIA 절).** `pending_action_id`는 대기마다 새로 발급한 불투명 ID여야 하고, PIA의 callback ID 형식(소문자로 시작, 64바이트 이하; `app/models.py` 9–22행)에 맞아야 한다. 현재 Harness `deliver`는 텍스트만 받으므로(`orchestrator.py` 314행), PIA가 같은 메시지에 버튼을 붙일지 별도 메시지를 보낼지 연동 계약에서 정해야 한다. 확인 대기를 전달 성공 뒤에만 저장한다는 기존 원칙은 유지한다.

줄일 부분: 복수 실행 호출은 새 대기 큐를 만들지 말고 위의 배치 검사 하나로 처리한다. 조사 루프의 새 반복 감지 규칙도 제안하지 않는다. 20회·60초가 이미 상한이다. 구현 후에는 복수 호출 ID 짝맞춤, 수정 메시지와 옛 버튼의 경쟁, 예산 초과 뒤 최종 답변을 각각 테스트하면 된다.

### Hermes 실제 코드와 대조

- Hermes의 [conversation loop](https://github.com/NousResearch/hermes-agent/blob/main/agent/conversation_loop.py)는 모델 응답에 `tool_calls`가 있으면 도구 round로, 없으면 최종 텍스트 경로로 간다. 따라서 B안의 “모델 하나가 도구 선택·인자·답변” 골격은 실제 Hermes와 맞는다. Hermes의 수많은 복구·세션·서브에이전트 단계는 PIA 요구에 따라 가져올 필요가 없다.
- Hermes의 [tool executor](https://github.com/NousResearch/hermes-agent/blob/main/agent/tool_executor.py)와 [batch planner](https://github.com/NousResearch/hermes-agent/blob/main/agent/tool_dispatch_helpers.py)는 병렬 가능한 호출만 묶고, 부작용 도구는 순서 경계로 두며, 병렬 결과도 원래 호출 순서와 ID에 맞춘다. B안의 읽기 동시 실행은 이 원칙과 맞지만, 금융 주문은 Hermes처럼 복수 부작용 호출을 순차 실행하지 말고 위 2번처럼 한 배치에 하나만 허용하는 편이 더 작고 안전하다.
- Hermes의 [finalizer](https://github.com/NousResearch/hermes-agent/blob/main/agent/turn_finalizer.py)는 반복 예산 소진 시 도구 없는 추가 모델 호출 한 번으로 요약 답변을 시도한다. B안의 `tool_choice=none` 최종 1회는 같은 핵심 방식이다. 다만 Hermes의 [입력 압력 계산](https://github.com/NousResearch/hermes-agent/blob/main/agent/conversation_loop.py)은 도구 schema도 포함한다. 위 3번의 예산 보정은 B안에도 실제로 필요하다.
- Hermes의 [memory inline executor](https://github.com/NousResearch/hermes-agent/blob/main/agent/inline_tool_executors.py)는 도구 호출 때 Memory를 쓴다. B안은 supersede되는 GENERATING 중 영속 변경을 막기 위해 신호만 기억하고 commit 뒤 기존 reviewer에 넘기므로, 이 지점은 Hermes를 그대로 복제하지 않는 것이 옳다. 자동 Memory 검토와 명시 요청의 구분만 정하면 된다.

## Claude 반영 (Codex 검토 대응)

- **B1 버튼·새 메시지 경쟁**: 새 메시지 수락 시 대기를 즉시 지우고, 확인·취소는 같은 `state_lock` 안에서 ID·만료·처리 중 여부를 확인하며 대기 꺼내기와 실행 확정을 한 번에 한다(§5). PIA 버튼 처리 때 회원 실행 자격 확인을 인계 항목에 넣었다.
- **B2 묶음 검사**: 실행 도구 둘 이상이면 아무것도 준비하지 않음, 읽기는 남은 한도까지만, 같은 URL 예약, 모든 호출 ID에 원래 순서대로 결과 하나씩(§1). 새 대기 큐나 반복 감지 규칙은 두지 않는다.
- **B3 예산**: 실제 요청 전체(도구 스키마·`tool_calls`·`tool` 메시지 포함)로 세고, 최종 호출은 도구를 빼고 같은 예산으로 확인한다. 들지 않으면 `CONTEXT_OVERFLOW`(§2).
- **Memory**: 사용자가 `memory` 도구(Hermes 방식)로 확정했다. 범위는 명시 요청 신호, 반영은 답변 확정 뒤 기존 reviewer(§6).
- **버튼 전달**: `deliver`에 `pending_action_id`를 넘겨 같은 메시지에 버튼을 붙인다. ID는 불투명·PIA callback 형식(§5).

## 구현 (Claude)

계획과 다르거나 계획에 없던 부분만 적는다.

- **Jev는 Memory 자동 검토에만 남긴다.** Jev는 루프 말고도 자동 Memory 검토에서 "문서를 고쳐 쓸 필요가 있는가"(`decide_memory_change`)를 판단한다. 루프와 무관하고 PIA 연결도 그대로라 `jev.py`에 이 기능만 남겼다(`choose_next`·64KB 한도·직전 Turn 발췌 제거). 뺄지는 사용자에게 묻는다(빼면 12시간 검토마다 luna가 문서를 다시 쓸지 스스로 판단).
- **memory 신호는 조사 한도·주문 준비 Turn에서도 반영한다.** 계획 6은 "부분 답변·실행 Turn은 NONE"이었지만, 그 규칙은 Jev가 answer와 함께만 정하던 구조 때문이었다. 이제 신호는 사용자의 명시 요청이라 버리지 않는다. `confirm` Turn은 첫 응답에서 `confirm`만 실행하므로 반영할 신호가 없다. 한도 알림에서 "Memory was not changed" 문장을 뺐다.
- **크기 때문에 도구를 빼고 다시 부를 때 Compaction을 다시 하지 않는다.** 첫 조립에서 이미 Compaction(Memory 검토 포함)을 했으므로, 도구 없는 재조립은 들면 쓰고 안 들면 `CONTEXT_OVERFLOW`다. 모델 호출이 두 번 반복되는 것을 막는다.
